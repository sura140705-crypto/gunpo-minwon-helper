## ① Main 은 포털이 아니라 고르는 곳이다

**[문제/배경]**
첫 화면을 「행정 분류를 탐색하는 포털」로 만들 것인가, 「내가 하려는 일을 빠르게 고르는
곳」으로 만들 것인가. 종전 첫 화면은 서식 8장을 **행정 분류 4구역**(여권 / 가족관계등록 신고 /
증명서 발급 / 부동산)으로 묶어 보여 주고 있었습니다. 그런데 시민은 「가족관계등록 신고」와
「증명서 발급」의 차이를 모르는 채로 옵니다 — 실제로는 **「등본 떼러 왔다」**고 말합니다.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 행정 분류로 1차 탐색 → 2차에서 서식 선택 | 시민이 **행정 분류를 알아야** 첫 걸음을 뗄 수 있습니다. 누름도 한 번 늘어납니다 |
| 검색창을 먼저 놓는다 | 8종에서는 훑는 것이 빠릅니다. 게다가 **철자·용어를 알아야** 칠 수 있습니다 |
| 「자주 찾는 민원」을 위에 크게 | 무엇이 자주인지 재지 않았습니다. 재기 전에는 지어내는 것입니다 |

**[최종 결정]**
- 8종을 **평평하게** 한 열로 늘어놓습니다. 1차 분류를 강제하지 않습니다.
- 카드의 **큰 글씨는 시민이 하려는 일**(「아이 출생 신고하기」),
  **작은 글씨는 행정서식명**(「출생신고서」)입니다. 창구와 말이 통해야 하므로 둘 다 냅니다.
- 보조 분류(`category`)는 데이터에만 두고 **화면에 드러내지 않습니다.**
- **검색 UI 는 지금 넣지 않습니다.** 다만 검색용 데이터(`keywords`·`aliases`)는
  카탈로그 8종에 **이미 채워 두었습니다** — 서식이 늘면 UI 만 붙이면 됩니다.

**[결정 이유]**
철학 §3 「Ask, Don't Form」의 첫 적용 지점이 여기입니다. 시민에게 행정 구조를 해석하게 하지
않는다는 원칙은 **서식 안에서만이 아니라 서식을 고르는 순간에도** 지켜져야 합니다.
20종 이하에서는 훑기가 탐색보다 빠르고, 고령자에게는 **선택지가 한 번에 다 보이는 편**이
단계를 밟는 것보다 쉽습니다.

**[향후 재검토 조건]**
- **서식이 20종을 넘을 때** → `category` 로 묶고 검색 UI 를 붙입니다.
- 현장에서 「원하는 민원을 못 찾겠다」는 관찰이 반복될 때 (수를 세어 근거로 남길 것)
- 기관이 취급 서식을 켜서 카드가 20장을 넘길 때

## ② ASK / PAPER / RAIL — 세 영역의 역할을 섞지 않는다

**[문제/배경]**
여권 화면을 세 영역으로 개편한 뒤(2026.08.21), 각 영역에 무엇을 넣을지 매번 다시 논쟁이
붙었습니다. 특히 오른쪽에 **버튼과 안내가 섞여 들어가려는 압력**이 계속 있었습니다.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 오른쪽에 [다음] 같은 주요 행동을 둔다 | 시선이 좌우로 튑니다. 「지금 할 일」이 두 곳에 있게 됩니다 |
| 오른쪽을 질문마다 바뀌는 도움말 패널로 | 질문이 넘어갈 때마다 화면 오른쪽이 요란해집니다(철학 §10 위반) |
| 영역을 상태에 따라 접었다 폈다 한다 | 접히고 펴질 때마다 **다른 화면처럼** 보입니다 |

**[최종 결정]**
세 영역의 역할을 다음으로 **고정**하고, 어떤 상태에서도 **생성·삭제하지 않습니다.**

| 영역 | 무엇을 두는가 | ⛔ 두지 않는 것 |
|---|---|---|
| **ASK** | **지금 시민이 해야 할 것** — 질문·선택·입력·[다음] | 참고정보 |
| **PAPER** | **실제 작성되고 있는 행정서식** | 안내문·버튼 |
| **RAIL** | **작성하는 동안 계속 참고할 가치가 있는 정보** | **지금 해야 할 행동** |

> **오른쪽에는 지금 해야 할 일이 아니라, 작성하는 동안 잊지 말아야 할 정보를 둔다.**

**[결정 이유]**
행동이 한 곳에만 있으면 시민은 **어디를 봐야 하는지 배우지 않아도 됩니다.** 서서 쓰고 뒤에
사람이 기다리는 상황에서, 「다음 버튼이 어디 있더라」를 매 화면 찾게 하면 안 됩니다.
영역을 접지 않는 것은 화면이 바뀔 때 **다른 제품처럼 보이지 않게** 하기 위한 것입니다.

**[향후 재검토 조건]**
- RAIL 이 계속 비어 보인다는 관찰이 있을 때 → **채우는 것이 아니라** 무엇을 넣을지 다시 정합니다.
  ⛔ 「비어 있으니 뭐라도 넣자」는 재검토 사유가 아닙니다(⑤ 참조).
- 세로 화면 전용 배치를 만들 때(⑦) → 그 배치에서 세 역할을 어떻게 지킬지 다시 씁니다.

> **이름에 대하여** — 이 영역을 문서에 따라 **RAIL** 또는 **INFO** 로 부릅니다.
> 정식 명칭은 **RAIL**(철학 §10 Context Rail · 코드 `rail-col`)이고, **INFO** 는 역할을
> 풀어 쓴 말입니다. 발표 자료에서는 처음 나올 때 **「RAIL(참고 정보)」** 로 풀어 쓰십시오.
> 셋 이상의 문서와 코드가 이미 RAIL 을 쓰고 있어 이름을 바꾸는 비용이 얻는 것보다 큽니다.

## ③ PAPER 가 중심이다 — 그리고 선명도가 곧 확정의 단계다

**[문제/배경]**
실제 행정서식은 장식이나 결과 화면이 아니라 **제품 경험의 중심**입니다. 그래서 처음에는
**모든 상태에서 실제 서식을 띄웠습니다** — 대기 시연 중에도, 카드에 마우스를 올렸을 때도,
골랐을 때도. 그런데 실제로 만들어 놓고 보니 두 가지 문제가 드러났습니다.

1. **카드를 눌러도 화면이 그대로인 것처럼 보였습니다.** hover 로 이미 그 서식이 떠 있었기
   때문에, 눌렀을 때 종이가 안 바뀝니다 — **누름이 아무 일도 하지 않은 것처럼** 읽혔습니다.
2. **빽빽한 정부 서식이 몇 초마다 바뀌어** 대기 화면이 시끄러웠습니다. 철학 §22 가 요구하는
   「조용한 대기」와 어긋났습니다.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 그대로 둔다(모든 상태에 실제 서식) | 위 두 문제가 그대로 남습니다 |
| hover 에서는 아무것도 안 띄운다 | 터치에는 hover 가 없어 **첫 화면이 비어 보입니다** |
| 고른 카드를 크게 강조해 「눌렸음」을 알린다 | 종이가 안 바뀌는 문제는 그대로입니다. 왼쪽만 요란해집니다 |
| 부가 서식(2쪽·별지)을 느리게 순환시켜 종이를 채운다 | **실물을 세어 보고 접었습니다.** 돌릴 것이 있는 서식이 여권 하나뿐이고, 그 한 장을 위해 그림 200KB 를 더 실어야 했습니다 |

**[최종 결정]**
종이 자리를 **네 단**으로 나누고, **실제 서식은 「고른 것」에만** 씁니다.

| 언제 | 종이 |
|---|---|
| 아무것도 안 고름 | 빈 윤곽 + 「서식을 골라 주세요」 |
| **시연 중** | **실루엣** — 서식 이름 + **그 서식이 묻는 항목**. 값이 한 줄씩 채워진다 |
| **hover · 키보드 포커스** | **실루엣** — 정지. 항목만 서 있고 값은 비어 있다 |
| **고름**(카드 펼침) | **실제 서식**, 흰 베일 한 겹으로 살짝 흐리게 |
| **작성(Writing)** | 실제 서식, 또렷 |

> **선명도가 곧 「어디까지 정해졌는가」다.**

**[결정 이유]**
「고름 → 작성」은 실제로는 페이지가 교체되는데도 **기하가 같아 화면이 움직이지 않습니다.**
그 순간을 무엇으로 알릴 것인가가 문제였는데, **종이가 또렷해지는 것**이 대신 말해 줍니다.
같은 장치로 위 두 문제가 함께 풀립니다 — 누름에 반응이 생기고, 대기 화면이 조용해집니다.
실루엣은 그림이 아니라 도형이라 **무게가 없어** 몇 초마다 바뀌어도 부담되지 않습니다.

**[향후 재검토 조건]**
- 실루엣이 「고장난 화면」으로 읽힌다는 관찰이 있을 때
- 시민이 hover 단계에서 이미 서식 내용을 확인하고 싶어 한다는 관찰이 있을 때
- 모션·시각 값이 확정되어(외부 검토 중) 베일 농도·전환 시간이 바뀔 때

### 그 뒤에 한 번 더 — 실루엣이 **채워지게** 했다 (2026.08.27)

처음 만든 실루엣은 **추상적인 줄**만 그어졌습니다. 조용하기는 했지만 「여기서 무엇을
할 수 있는가」를 말하지 못했고, 지나가는 사람이 멈춰 설 이유가 없었습니다.

지금은 **그 서식이 실제로 묻는 항목**이 왼쪽에 서고, 오른쪽 칸에 **값이 한 줄씩** 채워집니다.
이 화면의 한 문장이 눈앞에서 일어납니다 — **「질문에 답하면, 신청서가 완성됩니다.」**

- ⚠️ 값은 **전부 가상 인물**이고 종이 아래에 **「작성 예시입니다」**라고 적습니다.
  앞사람 개인정보가 남아 있는 것처럼 보이면 이 제품의 가장 큰 강점이 그 자리에서 무너집니다.
- ⚠️ 주민등록번호 뒷자리는 **가상값이라도 가립니다**(`900101-●●●●●●●`).
  늘 켜져 있는 화면에 숫자 13자리가 통째로 떠 있는 그림 자체를 만들지 않습니다.
- ⚠️ 한 카드에 머무는 시간을 **1.8초 → 2.8초**로 늘렸습니다. 읽을 것이 생겼기 때문입니다.
- ⛔ 폐기한 **Generic Paper**(가상의 ○○○신청서)를 되살린 것이 아닙니다. 이것은 **실제 8종
  각각의 항목**이고, 종이는 여전히 실루엣입니다(실제 서식 그림은 「고른 것」에만).

> 설계 방향**이었습니다. 위 이유로 2026.08.27 에 정정됐습니다.

## ④ 별도 Start 화면을 두지 않는다 — 카드가 그 자리에서 펼쳐진다

**[문제/배경]**
민원을 고른 뒤 **작성을 시작하기 전에** 무엇을 준비해야 하는지, 얼마나 걸리는지 알려 줄
자리가 필요했습니다. 처음에는 이것을 **별도의 Start 페이지**로 설계했습니다(구조동결 v1).

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| **별도 Start 페이지** | 누름이 한 번 늘고, Main 에서 이미 고른 것을 **다시 확인**시키는 중복이 생깁니다. Start 가 하려던 셋 중 둘은 이미 다른 곳이 하고 있었습니다 |
| 카드를 누르면 곧바로 Writing | **잘못 누른 사람이 되돌아올 길이 없습니다.** 고령자에게 특히 위험합니다 |
| 준비물을 모달로 띄운다 | 모달은 닫아야 하는 것이라 **또 하나의 누름**입니다. 읽지 않고 닫습니다 |

**[최종 결정]**
카드를 누르면 **그 자리에서 아래로 펼쳐져** 설명 · 걸리는 시간 · 준비물 · [작성 시작] 을 냅니다.
**[작성 시작]을 눌러야** 서식으로 갑니다. 같은 카드를 다시 누르면 접힙니다.

```
Main → (카드 펼침 = 필요한 경우의 사전 확인) → Writing → Review → Print → Clear → Main
```

- ⛔ **막지 않습니다.** 준비물이 없어도 [작성 시작]으로 갈 수 있습니다.
- ⚠️ **없는 것을 지어내지 않습니다.** 준비물·소요시간이 없는 서식은 그 줄을 아예 내지 않습니다.
  지금은 **여권만** 채워져 있고 나머지 7종은 설명 한 줄입니다.
- ⚠️ 경로가 정해진 뒤의 준비물(성인/미성년·본인/대리)은 **각 서식 안의 `ready` 가 맡습니다.**
  기존의 안정된 `SCREENS.ready` 기능을 제거하지 않았습니다 — 역할이 다릅니다.

**[결정 이유]**
Start 가 하려던 일은 셋이었습니다 — ① 고른 것을 되짚고 ② 얼마나 걸리는지 알리고
③ 준비물을 말한다. **①은 오른쪽에 그 서식이 뜨는 것으로 이미 이뤄지고**, ③은 경로가
정해져야 정확해져서 각 서식이 이미 하고 있었습니다. 남는 것은 ②뿐인데,
**그 한 줄 때문에 화면을 하나 더 세우고 누름을 하나 더 시킬 수는 없었습니다.**
카드 펼침은 화면을 늘리지 않고 같은 말을 합니다.

**[향후 재검토 조건]**
- 사전 확인이 **반드시** 필요한 민원이 생겼을 때(예: 준비물이 없으면 접수 자체가 불가능한 서식)
  → 그 서식에 한해 `ready` 를 강화하되, ⛔ **막는 화면을 새로 만들지는 않습니다.**
- 카드 펼침판이 길어져 목록이 심하게 출렁일 때

> ✅ **Ready 의 정의는 2026.08.27 에 [⑱](#d18) 로 못 박혔습니다** — 서식별 선택 상태이고,
> 공통 화면을 만들지 않으며, 7종에 없는 것이 정상입니다.

> ⚠️ 이 결정은 **「상세페이지」를 만드는 것이 아닙니다.** 페이지는 늘지 않았습니다 —
> 같은 화면 안 카드가 열릴 뿐입니다.

## ⑤ RAIL 에는 「지금 할 일」이 아니라 「잊지 말아야 할 것」을 둔다

**[문제/배경]**
오른쪽 영역은 **비어 보이기 쉽습니다.** 그래서 무엇으로든 채우려는 압력이 계속 생깁니다 —
배너, 홍보, 도움말, 버튼.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 질문마다 바뀌는 맥락 도움말 | 질문이 넘어갈 때마다 오른쪽 전체가 바뀌어 **화면이 요란**해집니다(철학 §10) |
| 안내를 넉넉히 넣어 공간을 채운다 | 스크롤이 생깁니다. 서서 쓰는 사람은 오른쪽을 스크롤하지 않습니다 |
| 배너 모음 / 외부기관 링크 | ⑥ 참조 |

**[최종 결정]**

| 어디 | 무엇 |
|---|---|
| **Main 의 RAIL** | 서비스 전체에 공통되는 개인정보·정보보호 안내를 **매우 간결하게** |
| **서식의 RAIL 상단** | 그 민원을 작성하는 동안 **계속** 참고할 가치가 있는 정보 |
| **서식의 RAIL 하단** | 공통 개인정보·보안 안내 (**바닥 고정** · 어떤 상태에서도 같은 자리) |

지키는 규칙:

- 정보 묶음은 **최대 2개 정도**
- 각 묶음은 **매우 짧게** · 긴 설명 금지
- **스크롤을 요구할 정도의 정보 금지**
- 배너 모음 금지 · 외부기관 홍보 영역으로 쓰지 않음
- **정보가 없으면 억지로 채우지 않고 여백을 허용**
- 질문마다 내용이 요란하게 바뀌는 보조 UI 로 만들지 않음 — 같은 상태 안에서는 **숫자만** 바뀝니다

**[결정 이유]**
오른쪽은 **읽지 않아도 되는 곳**이어야 합니다. 읽어야만 진행할 수 있는 것을 여기 두면
시민은 좌우를 번갈아 봐야 하고, 그 순간 세 영역은 실패합니다. 안정적으로 **거기 있다는 사실**
자체가 안심을 만듭니다 — 그래서 비어 있는 편이 잘못 채운 것보다 낫습니다.

**[향후 재검토 조건]**
- 7종에 RAIL 을 신설할 때(⑩) → 서식별로 무엇을 상단에 둘지 하나씩 정합니다.
- 1366×768 등 낮은 해상도에서 RAIL 항목이 겹치는 문제가 확인됨 → 별도 과제
  (실제 키오스크는 1920×1080 또는 1080×1920 이라 현장에서는 드러나지 않습니다)

> ⚠️ 개인정보 안내 **문구는 실제 동작을 넘지 않습니다.** ⑭ 를 함께 보십시오.

## ⑦ 가로와 세로를 하나의 배치로 억지로 풀지 않는다

- ⛔ **가로 UI 를 세로 대응 때문에 희생시키지 않습니다.**

**[지금 상태]** 세로에서는 세 영역을 **위아래로 쌓습니다.** 전용 배치가 아니라 임시 대응입니다.

스크롤을 모르는 시민에게는 보기 문제가 아니라 기능 문제였습니다.

## ⑧ 「크게 보기」는 zoom 이 아니라 접근성 모드다

**[문제/배경]**
고령자를 위해 화면을 키우는 기능이 필요한데, 브라우저 zoom 은 **레이아웃째 확대**라
한 화면에 들어오던 것이 잘리고 스크롤이 생깁니다.

**[검토한 대안]**
① 브라우저 zoom ② 글자 크기만 키우기 ③ 기본 보기 자체를 크게 만들고 별도 모드 없이 가기

**[최종 결정]**
- 「크게 보기」는 **글자 · 조작 영역 · 간격을 함께** 조정하는 **접근성 모드**입니다.
- 세 영역 비율도 함께 바뀝니다 — 일반 **2:3:1** → 크게 **5:5:2**.
- **기본 보기는 일반 사용자에게 적절한 정보 밀도와 세련된 화면**을 유지합니다.
  ⛔ 기본 보기를 지나치게 크게 만들어 **두 모드의 차이가 없어지게 하지 않습니다.**
- 비율은 토큰(`--cols`)으로 관리해 실물 화면을 보고 미세조정합니다.

**[결정 이유]**
크게 보기의 목적은 **PDF 확대가 아니라 질문·입력·조작 UI 의 접근성**입니다(철학 §13).
그래서 왼쪽 질문면이 넓어지고, **그만큼 가운데 종이는 오히려 작아집니다.**

> ⚠️ **이것은 버그가 아니라 받아들인 결과입니다.** 서식을 크게 보는 길은
> 따로 있습니다 — 종이 확대·스크롤과 [미리보기].
> ⛔ 이것을 되돌리려면 [`디자인검토/2026.08.24-디자인-결정.md`](디자인검토/2026.08.24-디자인-결정.md) §6-1 을 먼저 고쳐야 합니다.

**[향후 재검토 조건]**
- 실물 1920×1080 에서 종이가 **읽을 수 없을 만큼** 작아진다는 관찰이 있을 때 →
  `--cols` 비율만 조정합니다(구조를 바꾸지 않습니다).
- 크게 보기를 켜는 시민이 거의 없다는 관찰이 있을 때 → **켜는 방법**을 먼저 의심합니다.

## ⑨ 대기 화면을 따로 두지 않는다 — 첫 화면이 스스로 시연한다

> **상태 : 구현됨** (2026.08.25 도입 · 2026.08.27 개편). 설계 방향이 아닙니다.

**[문제/배경]**
공용 PC 앞에서 시민이 **「이걸 내가 만져도 되나?」**라고 느끼면 안 됩니다(철학 §22).
그런데 아무도 안 쓸 때 화면이 그냥 떠 있어서, **써도 된다는 신호가 없었습니다.**

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 별도 Idle 화면 + 시정홍보·캐러셀 | 철학 §22 가 명시적으로 금합니다. 광고판이 됩니다 |
| **별도 Idle 화면 + 가상 신청서가 저절로 채워짐**(v1·v2 설계) | 화면이 하나 늘고, **「깨어남」이라는 전환을 새로 설계**해야 하고, 가상 종이(Generic Paper)를 따로 만들어야 했습니다 |
| 화면 보호기 · 검은 화면 | 「고장났나?」로 읽힙니다. 쓰라는 신호의 정반대입니다 |

**[최종 결정]**
**대기 화면을 만들지 않습니다.** 첫 화면이 스스로 시연합니다.

- 아무도 안 건드리면 **왼쪽 카드를 하나씩 짚으며** 가운데 종이를 그 서식의 실루엣으로 바꾸고,
  그 위에 **줄을 한 줄씩 그어** 갑니다 — 누군가 쓰고 있는 것처럼 보입니다.
- **마우스가 움직이기만 해도**(키·터치·휠도) 멈추고 기본 상태가 됩니다.
- 다시 시연으로 돌아가는 시간은 서식 8종과 **같은 값**(`idleMs`, 기본 3분)입니다.
- ⛔ 빠른 pulse · 튀는 효과 · 캐러셀 · 동시 다중 애니메이션을 쓰지 않습니다.
- ⛔ **시연이 짚는 카드에 「골라짐」 표시를 쓰지 않습니다.** 시연이 끝난 뒤 시민이 고른 것처럼
  남으면 안 됩니다. 코드에서도 다른 이름(`.demo-on`)을 씁니다.
- ⚠️ **`prefers-reduced-motion` 이면 시연을 아예 돌리지 않습니다.** 정적인 경험을 제공합니다.

**[결정 이유]**
철학 §22 가 대기 화면에 요구하는 것은 둘입니다 — ①「써도 된다」를 알릴 것,
②「실제 서비스로 넘어갈 때 다른 제품처럼 느껴지지 않을 것」.
**②는 화면을 나누지 않으면 저절로 지켜지고**, ①은 **쓰는 모습을 그대로 보여 주는 것**보다
잘 알리는 방법이 없습니다. 가상 신청서 한 장이 채워지는 것보다, **진짜 목록이 짚히고

## ⑪ 인쇄물을 픽셀로 못 박는다

**[문제/배경]**
이 프로그램의 결과물은 화면이 아니라 **창구에 내는 종이 한 장**입니다. 값이 서식 위
절대좌표에 얹히는 구조라, **1pt 밀리면 접수처 스캐너가 못 읽습니다.**
그런데 화면 디자인은 계속 바뀝니다. **디자인을 바꾸다 인쇄물을 망가뜨릴 위험**이 상시로 있습니다.

**[검토한 대안]**
① 사람이 눈으로 확인 ② 좌표값 단위 테스트 ③ 인쇄 결과를 **이미지로 비교**

**[최종 결정]**
**인쇄 결과 19쪽(8종 × 작성예시 2)을 기준선 이미지와 픽셀 비교**합니다.
「전부 0px」이 기본값이고, 달라졌다면 **왜 달라졌는지 `CHANGELOG.md` 에 적어야** 기준선을
갱신할 수 있습니다.

```bash
python tools/verify-print.py              # 8종×예시2 = 19쪽
python tools/verify-print.py --electron   # 키오스크와 같은 조판 + 용지(A4) 검사
```

**[결정 이유]**
이것이 **디자인을 마음 놓고 바꿀 수 있게 하는 장치**입니다. 화면을 아무리 고쳐도 종이가
안 바뀐다는 것을 매번 기계가 확인해 주기 때문에, 개편을 두려워하지 않아도 됩니다.
2026.08 의 세 차례 대규모 화면 개편이 모두 **인쇄물 0px** 로 끝난 것이 그 증거입니다.

⚠️ Chrome 만으로는 부족했습니다. **실제 인쇄가 지나가는 Electron 경로**를 따로 검사하지
않아 2026.08.12 에 용지 사고가 그 틈으로 빠져나갔습니다(`docs/GOTCHAS.md ㉝`).

**[향후 재검토 조건]**
- 서식이 추가될 때마다 **기준선에 그 서식을 넣습니다**(19쪽이 늘어납니다).
- 법정서식이 개정될 때 → 기준선을 갱신하고 **개정 사실을 CHANGELOG 에 남깁니다.**

## ⑫ 화면 색을 기관 대표색 하나에서 계산한다

**[문제/배경]**
같은 배포본을 여러 기관이 씁니다. 기관마다 대표색이 다릅니다(군포는 파랑, 안양은 초록…).
색을 화면 곳곳에 하드코딩하면 **기관을 바꿀 때마다 소스를 고쳐 다시 빌드**해야 합니다.

**[최종 결정]**

**[결정 이유]**

설치본을 그대로 두고 설정만 바꾸면 되므로, 받는 기관에 개발 역량이 필요 없습니다.

**[향후 재검토 조건]**

## ⑭ 개인정보는 구조와 동작으로 한다 — 못 하는 것은 못 한다고 적는다

**[문제/배경]**
공용 PC 입니다. **뒷사람에게 앞사람 내용이 보이면 안 됩니다.**
동시에, 시민을 겁주는 경고문으로 화면을 채우면 안 됩니다(철학 §11).

**[최종 결정 — 하는 것]**

| | |
|---|---|
| 저장하지 않음 | 입력값은 메모리에만. `localStorage`·`sessionStorage`·`indexedDB` 미사용 |
| 보내지 않음 | 외부 통신 없음(오프라인) |
| 무동작 초기화 | 3분(설정 가능) · 마지막 **30초 카운트다운 경고** → 첫 화면으로, 값 소멸 |
| 인쇄 후 초기화 | 화면을 **즉시 완전히 덮고** 5초 뒤 첫 화면으로 |
| 첫 화면 | 지울 것이 없으므로 **경고 없이** 조용히 시연으로 돌아감 |
| 색 | 개인정보 안내에 **빨강을 쓰지 않습니다.** 빨강은 실제 오류·진행불가에만 |

**[최종 결정 — 못 하는 것]**

> **이 두 가지를 문서·안내·발표에서 「된다」고 말하지 않습니다.**

| | 왜 못 하나 | 어떻게 대응했나 |
|---|---|---|
| 인쇄를 **취소**했을 때 초기화하지 않기 | 브라우저가 인쇄와 취소를 **구분해 주지 않습니다** | **취소해도 초기화됩니다.** 인쇄 전 안내에 그렇게 적어 두었습니다 |
| 「PDF로 저장」 차단 | 앱(JS)이 인쇄창 목적지를 제어할 수 없습니다 | **PC 설정의 몫**입니다. 설치 안내에 절차를 넣었습니다 |

**[결정 이유]**
개인정보 보호는 **색이나 문구가 아니라 구조와 동작**으로 구현합니다. 그리고
**할 수 없는 것을 할 수 있다고 적으면 그 문서 전체의 신뢰가 무너집니다.** 특히 이 기록은
발표와 상위기관 제안의 근거로 쓰이므로, 한계를 먼저 적는 편이 안전합니다.

**[향후 재검토 조건]**

## ⑮ 카탈로그를 한 곳에 둔다 · 검색은 20종부터

| 아이콘 폰트(Material·Font Awesome 등) | 설치·CDN 이 필요합니다. **오프라인에서 못 씁니다** |
| 아이콘을 아예 없앤다 | 목록을 훑을 때 형태가 주는 단서를 잃습니다. 고령자에게 글자만 있는 목록은 더 어렵습니다 |
| 서식 종류별로 색을 달리한 아이콘 | 대표색이 기관마다 바뀌는데 8가지 색을 따로 두면 **색 체계가 두 벌**이 됩니다 |

**[최종 결정]**
**인라인 SVG 선 아이콘 한 벌**을 코드 안에 직접 둡니다.

- **같은 문법** — 24 격자 · 굵기 1.7 · 둥근 끝. 하나만 달라도 한 벌로 안 보입니다
- **`currentColor`** — 평소에는 **잉크색**(무채색)을 따르고, hover·포커스·**고른 카드**에서만
  대표색이 됩니다. 그때는 색이 **「골라짐」이라는 뜻**을 가집니다
- 카탈로그의 `icon`(이모지)은 **대비책으로 남겨** 둡니다 — 아이콘이 없는 서식이 생기면 그것으로 물러납니다

**[결정 이유]**
철학 §15 는 **색마다 하나의 역할**을 주고 §1 은 장식 목적의 여러 색을 금합니다.
이모지는 그 두 가지를 동시에 어깁니다 — 게다가 같은 배포본이 기관마다 다르게 보입니다.
단색 선 아이콘은 **오프라인 제약을 지키면서** 색 체계를 하나로 유지합니다.

> ⚠️ **사망·이혼은 감정이 실리는 민원입니다.** 상징을 세게 쓰지 않았습니다 —
> 십자가·비둘기·깨진 하트 대신 **국화 한 송이**와 **담담한 두 사람**으로 두었습니다.

**[향후 재검토 조건]**
- 외부 시각 검토에서 **더 나은 한 벌**을 받았을 때 → 통째로 갈아 끼웁니다.
  ⛔ 한두 개만 바꾸지 마십시오. 한 벌이 아니게 됩니다
- 서식이 늘어 아이콘이 20개를 넘을 때 → 그때는 세트를 파일로 분리할지 다시 봅니다

## ⑰ 모션은 세 박자다 · 오류와 개인정보 차단은 즉시

**[문제/배경]**
모션 토큰이 **아예 없었습니다.** 값이 5개 원본에 8곳 흩어져 있었고 종류가 벌써
다섯이었으며(`.12` `.15` `.2` `.22` `.34s`), easing 은 대부분 **방치**돼 브라우저 기본값으로
굴러갔습니다. 이 상태로는 **밖에서 시안을 받아도 붙일 자리가 없었습니다.**

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 지금대로 각 자리에서 정한다 | 이미 다섯 가지로 흩어졌습니다. 놔두면 계속 늘어납니다 |
| 동작마다 토큰을 둔다(10개 이상) | 흩어진 것을 이름만 바꿔 옮기는 일입니다 |
| 모션을 아예 없앤다 | 종이가 갈아 끼워지는 것·펼침판이 열리는 것을 **툭** 바꾸면 시선이 튑니다 |

**[최종 결정]**
**세 박자 + 세 곡선, 여섯 개로 고정**합니다. ⛔ 늘리지 않습니다 — 늘어나는 순간 다시 흩어집니다.

```
--dur-quick  120ms   눌린 표시·hover — 손을 뗄 무렵 반응이 보여야 한다
--dur-base   200ms   펼침·접힘·나타남 — 시민이 직접 일으킨 상태 변화
--dur-calm   320ms   종이 갈아끼우기·큰 비율 변화 — 위치가 어디로 갔는지 따라갈 시간
--ease-out   cubic-bezier(.2,0,0,1)     들어오는 것
--ease-in    cubic-bezier(.4,0,1,1)     나가는 것
--ease-move  cubic-bezier(.4,0,.2,1)    자리를 옮기는 것
```

그리고 **움직이지 않기로 한 것 둘**:

| | 왜 |
|---|---|
| **입력 오류 표시** | 진행 불가 상태는 지연 없이 나타나야 합니다. 색이 서서히 변하면 **오류를 알아채는 것이 늦어집니다** |
| **인쇄 후 개인정보 덮개** | 개인정보 보호는 **연출보다 차단 시점**이 먼저입니다. 즉시 완전히 덮습니다 |

**[결정 이유]**
값은 **2026.08.27 외부 검토(과제 A)로 받았습니다.** 지속시간은 종전에서 20ms 씩만
움직였고 동작 배정 12개 중 **6개는 이미 그대로였습니다** — 밖에서 온 답이 지금 코드를
확인해 준 셈입니다. 실제로 바뀐 것은 **easing** 이고, 제각각이던 곡선이 한 가족이 됐습니다.

「움직임은 상태를 설명할 때만 쓴다」(철학 §17)를 지키려면 **값이 한 곳에 있어야** 합니다.
지금은 여섯 줄만 갈아 끼우면 9개 화면이 함께 바뀝니다.

**[향후 재검토 조건]**
- 현장 PC 에서 **끊겨 보인다**는 관찰이 있을 때 → 값을 줄이는 것이 먼저입니다
- 대기 시연의 리듬은 **의뢰서 D** 에서 따로 정합니다 — 값 하나가 아니라 하나의 연출입니다
- ⛔ 토큰을 **일곱 개째** 만들자는 말이 나오면, 그 동작이 정말 다른 박자인지 먼저 따집니다

> **아직 붙이지 않은 넷** — 값이 아니라 **구조를 바꿔야** 하는 것들입니다.
> · 인쇄 전 모달(`display` 로 여닫아 전환이 안 걸린다)
> · 크게 보기 전환(가능하지만 성능을 못 쟀고, **종이가 작아지는 것이 오히려 강조될** 위험)
> · 질문 → 다음 질문 / Current Focus 이동(둘 다 `innerHTML` 재생성이라 transition 이 안 걸린다.
>   특히 Current Focus 는 **인쇄 경로 옆**이라 손대는 비용이 크다)

## ⑱ Ready 는 서식별 선택 상태다 — 공통 화면을 만들지 않는다

**[문제/배경]**
민원을 고른 뒤 **작성을 시작하기 전에** 준비물과 걸리는 시간을 알려 줄 자리가 필요합니다.
그런데 그 자리를 **모든 서식에 똑같이** 둘 것인가가 정해지지 않은 채로,
`SCREENS.ready`(여권 안) · 카탈로그의 `ready`(카드 펼침판) 두 곳에 흩어져 있었습니다.
「7종에는 Ready 가 없다」가 **결함인지 정상인지** 아무도 말하지 않았습니다.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 공통 **Start/Ready 화면**을 세운다 | 📌 ④ 에서 이미 폐기했습니다. 누름이 늘고, 고른 것을 다시 확인시키는 중복이 생깁니다 |
| **7종에도** Ready 화면을 새로 만든다 | **필요성이 확인되지 않았습니다.** 7종의 준비물은 지금 비어 있고, 채우려면 부서 확인이 먼저입니다. 없는 것을 지어내는 일이 됩니다 |
| 카탈로그 `ready` 로 **공통 Ready 화면을 생성**한다 | 경로가 정해져야 정확해지는 준비물(성인/미성년·본인/대리)을 **경로 이전에** 말하게 됩니다 |

**[최종 결정]**
Ready 를 **서식별 선택 상태(Form-specific optional state)** 로 정의합니다.

```
Main → 상세(카드 펼침판) → [Ready — 필요한 서식만] → Writing
```

| | |
|---|---|
| ⛔ **공통 Start/Ready 화면** | 만들지 않습니다 |
| ✅ **여권** | `SCREENS.ready` 를 **여권의 공식 Ready 로 유지**합니다 |
| 📌 **나머지 7종** | **실제 업무상 필요성이 확인되기 전까지 새로 만들지 않습니다** |
| 📌 **카탈로그의 `ready`** | 공통 화면을 만들기 위한 데이터가 **아닙니다.** 서식별 준비정보를 관리하는 **metadata** 입니다. 지금은 카드 펼침판이 그것을 읽어 보여 줄 뿐입니다 |

**[결정 이유]**
준비물은 **서식마다 있고 없고가 다릅니다.** 여권은 사진·수수료·기존 여권이 필요하지만
출생신고서는 그런 것이 없습니다. 모든 서식에 같은 자리를 두면 **비어 있는 화면**이
생기고, 그것을 채우려다 **없는 것을 지어내게** 됩니다(⑮ 와 같은 원칙).

그리고 「Ready 가 없다」가 **정상이라고 못 박아 두어야** 다음 사람이 그것을 결함으로
보고 채우려 들지 않습니다.

**[향후 재검토 조건]**
- 어떤 서식에서 **준비물이 없으면 접수 자체가 불가능**하다는 것이 부서 확인으로 나올 때
  → **그 서식에만** Ready 를 만듭니다. ⛔ 공통 화면으로 만들지 않습니다
- 카탈로그 `ready` 가 7종에도 채워질 때 → 카드 펼침판이 자동으로 보여 줍니다.
  ⛔ 그것을 화면 신설의 근거로 삼지 않습니다

## ⑲ 창구 전환은 정상 경로다 — 오류가 아니다

**[문제/배경]**
여권에는 **창구 전환**이 있습니다 — 기관 기준상 키오스크에서 끝낼 수 없는 경우
(관용·외교관 여권, 대리 신청, 판단이 어려운 경우 등) 작성을 멈추고 창구로 보냅니다.
그런데 이것이 **흐름도 어디에도 없었습니다.** 문서에 없으면 다음 사람은 이것을
「실패 처리」로 보고 없애려 들거나, 오류 화면처럼 디자인하게 됩니다.

**[검토한 대안]**

| 안 | 왜 버렸나 |
|---|---|
| 오류 처리로 본다 | 철학 §8 「직원에게 묻는 것은 실패가 아니다」와 정면으로 어긋납니다 |
| 없애고 **끝까지 받는다** | 기관 기준상 못 받는 것을 받으면, 시민이 **다 작성한 뒤 창구에서 되돌아갑니다.** 더 나쁩니다 |
| 흐름도에서 빼 둔다(현상 유지) | 문서에 없으면 없어집니다. 실제로 이번 정리 전까지 어느 문서에도 없었습니다 |

**[최종 결정]**
**흐름도에 정식으로 넣습니다.** 필요한 행정적 판단을 직원에게 넘기는 **정상 기능**입니다.

```
일반 경로     Main → [Ready] → Writing → Review/Print → Clear → Main
직원 도움 경로 Main → [Ready] → Writing → Human Handoff → Clear/정리 → Main
```

지키는 것:

| | |
|---|---|
| ⛔ **개인정보를 화면에 표시하지 않습니다** | 시민이 이 화면을 **사진 찍어 창구에 보여 줍니다** |
| ⛔ **안내표 인쇄물에도 개인정보를 넣지 않습니다** | 창구에 전할 것은 「누구인지」가 아니라 **「왜 창구로 왔는지」**입니다 |
| ⛔ **오류처럼 보이게 하지 않습니다** | 빨강은 실제 오류·진행불가에만(⑭·철학 §11) |
| ✅ **작성을 멈춥니다** | 단계 표시와 RAIL 정보를 비웁니다 — 더 물을 것이 없다는 뜻입니다 |

**[결정 이유]**
민원 업무에는 **시스템만으로 판단할 수 없는 상황이 실재합니다.** 그것을 오류로 다루면
시민은 자기가 뭘 잘못한 줄 알고, 직원은 「이 기계가 또 안 된다」로 받아들입니다.
**정상 경로로 두면 둘 다 사라집니다** — 이 도구가 하는 일에 「직원에게 넘기기」가
처음부터 포함돼 있는 것이 됩니다.

**[향후 재검토 조건]**
- 창구 전환 비율이 **너무 높다**는 관찰이 있을 때 → 사유 코드별로 세어 봅니다.
  ⛔ 기능을 없애는 것이 아니라 **어느 조건이 과한지**를 봅니다
- 7종에서도 창구 전환이 필요한 판단 지점이 확인될 때 → 그 서식에 추가합니다

> ⚠️ **실제 종료 동작에 결정된 흐름과 다른 곳이 하나 있습니다** —
> [처음으로] 는 `resetAll()` 이라 **Main 으로 가지 않고 여권 첫 화면에 남습니다**
> (개인정보는 그 자리에서 지워지고, 무동작 3분 뒤 Main 으로 자동 회복).
> 📌 **이번 단계에서 고치지 않았습니다.** 자세한 것은
> [`UIUX_HANDOFF.md`](UIUX_HANDOFF.md) §9-4.

> ⚠️ 7종의 「이 단계는 잘 모르겠어요」는 **창구 전환이 아닙니다.** `state.unsure` 에 표시만
> 하고 다음 단계로 넘어가는데, **그 표시를 읽는 곳이 없습니다** — 시민의 「모르겠다」가
> 조용히 사라집니다. 알려진 사실로 기록해 둡니다(`UIUX_HANDOFF.md` §9-3).
