## 1. 현재 단계

### 무엇이 있는가

법정 민원신청서 **8종**의 작성지원 기능이 **구현됨** 상태입니다. 목록과 화면 문법은
[`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) §3·§4 에 있습니다.

구조는 이미 **공통 엔진 + 서식별 설정**으로 한 번 갈라져 있습니다.

| | 무엇 | 상태 |
|---|---|---|
| 공통 엔진 | `engine/engine.js` · `engine/base-product.html` | **구현됨** · 엔진 서식 7종이 공유 |
| 서식별 설정 | `forms/<이름>.config.js` | **구현됨** · 7종 |
| 손작성 1종 | `passport-helper-v1.html` | **구현됨** · 여권만 엔진 밖에 있습니다 |
| 기관별 설정 | 설치본 환경설정 창 3탭 | **구현됨** — [`타지자체-확산.md`](타지자체-확산.md) §A |
| 인쇄물 회귀 검증 | `tools/verify-print.py` (19쪽 픽셀 비교) | **구현됨** |

즉 **「신청서마다 다른 것」을 한 파일에 모으는 일은 이미 하고 있습니다.** 이 문서가 말하는
분리는 그것을 처음 시작하자는 이야기가 아니라, **이미 있는 경계선을 어디까지 밀 것인가**의
이야기입니다.

### 지금 방식의 한계

지금 구조로도 서식은 늘릴 수 있습니다. 다만 **늘리는 일을 할 수 있는 사람이 개발자뿐**입니다.

| 한계 | 구체적으로 |
|---|---|
| **콘텐츠가 실행 코드다** | `forms/*.config.js` 는 JavaScript 입니다. `buildVals(state)`·`body(A)`·`required(state)`·`checkVisible()` 이 **함수**라, 업무 담당자가 직접 읽고 고치기 어렵습니다 |
| **업무지식이 개발자를 거쳐야 한다** | 담당 부서가 정한 기준을 개발자가 코드로 옮깁니다. [`EXPANSION_PLAYBOOK.md`](EXPANSION_PLAYBOOK.md) §1 의 14단계에 「담당 부서」가 정할 일이 이미 표시돼 있지만, **옮기는 사람은 여전히 개발자**입니다 |
| **콘텐츠에 신원이 없다** | 서식 개정일·소관업무·법령 근거가 config 머리말 **주석**으로만 있습니다(예: `forms/naming.config.js` 의 구본/신본 경고). 사람이 읽는 글이지 기계가 다루는 값이 아닙니다 |
| **버전이 저장소 단위다** | 변경이력은 `CHANGELOG.md` 한 곳에 쌓입니다. 「여권 콘텐츠만 v1.2 → v1.3」처럼 **서식 하나 단위로** 끊을 수 없습니다 |
| **좌표 작업이 가장 비싸다** | 확산 문서가 이미 적고 있는 사실입니다 — 그런데 그 비용을 **한 번만 치르면 전국이 재사용**할 수 있습니다(§7) |

## 2. 확장 방향

### 하려는 것

> **개발자가 신청서를 계속 추가하는 구조에서, 업무를 가장 잘 아는 담당자가
> 신청서 콘텐츠를 만드는 구조로 옮긴다.**

세 단계로 봅니다.

| 단계 | 무엇 | 상태 |
|---|---|---|
| **현재** | 개발자가 8종을 직접 구현 | **구현됨** |
| **다음** | 공통 플랫폼과 신청서별 콘텐츠를 분리 (§3·§4) | **분리 예정** |
| **장기** | 현업 담당자가 AI의 도움을 받아 콘텐츠를 만들고 검증·공유 (§5·§7) | **장기 비전** |

### 하지 않으려는 것

- ⛔ **모든 행정업무를 시스템화하는 일**이 아닙니다. 대상은 **법정 신청서**로 한정합니다(§9).
- ⛔ **서식을 새로 디자인하는 일**이 아닙니다. 이 원칙은 지금과 같습니다
  → [`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) §1.
- ⛔ **시민이 쓰는 실행 단계에 생성형 AI를 넣는 일**이 아닙니다. 이 경계는 §6 에서
  따로 다룹니다. **어느 단계에서도 무너뜨리지 않습니다.**

## 3. 공통 플랫폼과 신청서 콘텐츠 분리

### 경계선을 긋는 기준

> **신청서 종류와 관계없이 필요한 것은 플랫폼, 그 업무에서만 필요한 지식은 콘텐츠.**

이 기준의 목적은 하나입니다 — **플랫폼을 만드는 사람이 업무지식을 모두 갖고 있지 않아도
되게 하는 것.**

### 플랫폼이 담당하는 영역

아래는 **신청서가 몇 종이든 같은 동작**입니다. 상태는 현재 코드 기준입니다.

| 영역 | 상태 |
|---|---|
| 준비사항 안내 · 질문 화면 표시 · 조건분기 실행 | **구현됨** |
| 입력값 관리 · 입력형식 정리(주민·전화·금액·날짜) | **구현됨** |
| 도움말·작성예시 표시 | **구현됨** |
| 누락 확인 · 최종확인(Review) | **구현됨** |
| 법정서식 미리보기 · 출력 | **구현됨** |
| 창구 문의 전환 | **부분 구현** — 경로는 공통, 사유 체계는 여권만 |
| 문의코드 표시 | **부분 구현** — 여권의 `P-01…` 만 |
| 기관 기본설정 · 프린터/출력설정 · 자동초기화 · 이용통계 | **구현됨** |
| **콘텐츠 버전 로딩** | **검토 중** — 지금은 빌드 시점에 인라인합니다(§8) |
| **검증도구와의 연계** | **부분 구현** — 도구는 있으나 콘텐츠가 스스로 검증 기준을 선언하지는 않습니다(§4) |

### 콘텐츠가 담당하는 영역

아래는 **그 신청서에서만 의미가 있는 업무지식**입니다.

- 어떤 질문을 할 것인가 / 어떤 순서로 물을 것인가
- 어떤 답변에서 흐름이 달라지는가
- 어떤 입력형식을 요구하는가
- 어떤 도움말을 보여줄 것인가
- 서식 어느 위치에 출력할 것인가
- **어디까지 일반적인 작성흐름으로 지원할 것인가**
- **어느 지점부터 담당자 확인이 필요한가**

> 📌 뒤의 둘이 특히 중요합니다. 이것은 기술 판단이 아니라 **업무 판단**이고, 개발자가
> 정할 수 없습니다. 지금도 [`EXPANSION_PLAYBOOK.md`](EXPANSION_PLAYBOOK.md) §1 이
> 「담당 부서 검토 필수」로 표시해 둔 자리입니다.

### 분리가 진행되면 달라지는 것

| | 지금 | 분리 후 (**분리 예정**) |
|---|---|---|
| 콘텐츠의 형태 | JavaScript 설정 파일 | 선언적 자료 + 꼭 필요한 곳에만 코드 |
| 새 서식을 붙이는 사람 | 개발자 | 담당자(초안) + 개발자(검토) |
| 검증 | 저장소 전체 도구를 돌림 | 콘텐츠가 자기 검증 기준을 들고 있음 |
| 배포 단위 | 저장소 전체 | 콘텐츠 단위 |

⚠️ **분리는 목적이 아니라 수단입니다.** 지금 구조로 충분한 부분까지 굳이 가르지 않습니다.
특히 좌표맵은 이미 서식별로 완전히 분리돼 있어 더 손댈 이유가 없습니다.

## 4. 신청서 콘텐츠 모델

### 신청서 1종 = 콘텐츠 1개

**법정 민원신청서 한 종을 독립된 콘텐츠 단위로 관리하는 방향**입니다.

콘텐츠 하나에 담길 수 있는 요소와, 그것이 **지금 어디에 있는지**를 나란히 적습니다.

| 요소 | 지금 어디에 있는가 | 상태 |
|---|---|---|
| 법정서식 원본 | `서식원본/*.pdf` + `engine/assets/<이름>.b64` | **구현됨** |
| 기재항목 | config 의 `stateKeys`·`stateDefaults` | **구현됨** |
| 항목별 질문 · 질문 순서 | config 의 `STEPS[]` (`q`·`title`·`n`) | **구현됨** |
| 조건별 분기 | `required(state)` · `checkVisible()` · `data-goto` | **구현됨** |
| 입력형식 및 검증규칙 | 입력칸 `type`(`jumin`·`phone`·`money`·`date`) | **구현됨** |
| 도움말 | `STEPS[].why` · `noticeItems` | **부분 구현** — 단계 단위이고 항목 단위 체계는 아닙니다 |
| 작성예시 | `applySample()` · `sampleLabels`/`sampleKinds` | **구현됨** · 2벌 |
| 법정서식 출력 위치 | `CO`(좌표맵) · `STEP_HL` · `extraPages()` | **구현됨** |
| 해당하지 않는 항목 처리 | `checkVisible()` — 조건 변경 후 잔상 방지 | **구현됨** |
| 담당자 확인이 필요한 지점 | 여권 코드에만 있습니다 | **부분 구현** |
| 문의코드 및 창구 안내 | 여권 `P-01…` | **부분 구현** |
| **서식명·소관업무·버전·개정일** | config **머리말 주석** | **분리 예정** — 기계가 읽는 값이 아닙니다 |
| **관련 법령·작성기준** | 코드에 없습니다 | **분리 예정** |
| **정상 출력 예시** | `tests/baseline/` 의 기준선 이미지 19쪽 | **부분 구현** — 저장소 단위로 묶여 있습니다 |
| **자동검증 기준 및 테스트 시나리오** | 도구가 바깥에서 정합니다 | **분리 예정** — 콘텐츠가 선언하지 않습니다 |
| **변경이력** | `CHANGELOG.md` (저장소 단위) | **분리 예정** — 콘텐츠 단위가 아닙니다(§8) |

> ⛔ **위 표의 요소가 전부 구현돼 있다는 뜻이 아닙니다.** 절반은 「지금 그 자리에 해당하는
> 것이 있다」는 뜻이고, **분리 예정**으로 적힌 다섯은 **지금 없습니다.**

### 이 모델이 주는 것

콘텐츠에 **신원**(이름·버전·개정일·근거)이 생기면 다음을 물어볼 수 있게 됩니다 — 지금은
사람이 기억하거나 주석을 찾아 읽어야 하는 것들입니다.

- 어떤 신청서 콘텐츠가 존재하는가 / 어떤 서식이 아직 지원되지 않는가
- 현재 적용 중인 서식 버전은 무엇인가 / 최근 개정 여부
- 누가 검증했는가 / 어떤 테스트를 통과했는가 / 어느 기관에서 사용 중인가

이 질문에 답할 수 있다는 것이 §7·§8 의 전제입니다.

## 5. 현업 담당자 중심의 콘텐츠 제작

**장기 비전**입니다. 지금 이런 도구는 **없습니다.**

### 지향하는 흐름

```
법정 신청서 불러오기
        ↓
서식 및 기재항목 분석
        ↓
질문·분기·도움말 초안 작성
        ↓
현업 담당자 검토·수정
        ↓
출력 위치 및 입력규칙 설정
        ↓
대표 사례 테스트
        ↓
자동검증
        ↓
콘텐츠 배포
```

### 지금 절차와의 관계

이 흐름은 [`EXPANSION_PLAYBOOK.md`](EXPANSION_PLAYBOOK.md) §1 의 **14단계를 대체하지
않습니다.** 정해야 할 것은 그대로이고, **정한 것을 콘텐츠로 옮기는 구간의 장벽만** 낮춥니다.

| 14단계 중 | 지금 | 지향 |
|---|---|---|
| ①②③ 서식 확보·업무목적·명칭 | 담당 부서 | 그대로 — **사람이 정합니다** |
| ④⑤ 질문 추출·시민 언어로 | 담당 부서 + 설계 | 초안을 도구가 만들고 **담당자가 고칩니다** |
| ⑥ 질문–서식 필드 매핑 | 설계 + 개발 | 후보를 도구가 제시하고 **사람이 확정합니다** |
| ⑦⑧ 준비물·RAIL | 담당 부서 | 그대로 — ⛔ **지어내지 않는다**는 원칙 유지 |
| ⑨⑩ 카탈로그·기관설정 | 개발 | 도구가 생성 |
| ⑪~⑭ 검증 | 개발 | 도구가 실행, **결과 판단은 사람** |

> ⚠️ **좌표 작업(⑥)은 가장 낙관하기 쉬운 자리입니다.** 인쇄물은 판독기·창구 접수용이라
> 「대충 맞으면」이 통하지 않습니다. 자동 제안이 가능해지더라도 **사람의 확인과
> `verify-print.py` 통과가 빠지는 구조는 만들지 않습니다.**

## 6. AI의 역할 — 제작 단계와 실행 단계를 가른다

### ⛔ 실행 단계의 원칙은 지금과 같습니다

> **시민이 사용하는 실제 서비스는 생성형 AI가 민원 내용을 실시간으로 판단하는
> 구조가 아닙니다. 앞으로도 그렇게 바꾸지 않습니다.**

지금의 원칙이자 앞으로의 원칙입니다.

```
사람이 업무기준과 자동화 범위를 결정
        ↓
AI를 활용해 구현·실험
        ↓
담당자와 결과 검증
        ↓
확정된 내용을 규칙으로 고정
        ↓
실제 서비스에서는 동일 입력에 동일 결과
```

나가는 것이 **판독기를 타고 창구에서 접수되는 법정 별지서식**이기 때문입니다. 실행할 때마다
달라질 수 있는 출력은 쓸 수 없습니다. 이 프로그램은 외부 통신을 하지 않고, 실행 경로에
모델 추론이 들어 있지 않습니다 — **구현됨**이고, 검증 방법은
[`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) §6 에 있습니다.

📌 **콘텐츠 제작 도구에 AI가 추가되더라도 이 경계는 그대로입니다.**

| | 누가 쓰는가 | AI |
|---|---|---|
| **제작 단계** | 담당자·개발자 | 초안 생성·분석 보조 (**장기 비전**) |
| **실행 단계** | 시민 | ⛔ **없음** — 규칙만 (**구현됨**) |

### AI가 지원할 수 있는 일

- 서식 항목 분석 보조
- 질문 초안 작성 · 행정용어를 시민 언어로 풀어쓰는 초안
- 조건분기 초안 · 도움말 초안
- 콘텐츠 구조 생성 · 반복적인 코드·설정 생성
- 테스트 케이스 생성 보조 · 변경된 서식 비교 보조

### 사람이 결정해야 하는 일

- 실제 업무기준 · 질문의 정확성 · 적용범위
- 대표적인 업무유형 · **자동화 가능 범위**
- **예외 및 창구전환 기준**
- **법정서식과의 일치 여부** · 최종 콘텐츠 승인

> **핵심 원칙** — AI가 업무기준을 결정하는 것이 아닙니다.
> **담당자가 이미 가진 업무지식을 실제 서비스 콘텐츠로 만드는 과정의 구현 장벽을 낮출 뿐**입니다.

## 7. 전국 공통 콘텐츠의 재사용

### 왜 재사용이 되는가

민원신청서는 법령 등에 따라 **전국에서 공통으로 쓰는 법정서식이 많습니다.** 그래서
**좌표맵 8종은 이미 전국 공통으로 재사용됩니다** — **구현됨**이고, 확산 실익의 근거로
[`타지자체-확산.md`](타지자체-확산.md) 머리말에 적혀 있습니다.

같은 콘텐츠를 기관마다 처음부터 다시 만들 필요가 없다는 뜻입니다.

### 지향하는 순환 (**장기 비전**)

```
공통 신청서 콘텐츠 제작
        ↓
공유
        ↓
각 기관에서 적용
        ↓
현장 담당자 검토·보완
        ↓
개선사항 공유
        ↓
공통 콘텐츠 개선
```

### 기관별 차이는 설정으로 가른다

> **기관마다 다른 값은 콘텐츠 코드가 아니라 설정으로 뺀다.**

이 방향은 이미 상당 부분 **구현됨** 상태입니다.

| 항목 | 상태 |
|---|---|
| 기관명 · 부서·창구 · 문의 전화 · 소재지 · 안내 문구 | **구현됨** (환경설정 창 · 기관 설정 탭) |
| 기관 로고 · 대표색 | **구현됨** — 색은 대표색 하나에서 계산합니다 |
| 사용할 민원서식 | **구현됨** — 끈 서식은 첫 화면에서 사라집니다 |
| 신고관청 표기 | **구현됨** — 부동산 신고서의 받는 곳 |
| 업무 기준(여권 접수 5가지) | **구현됨** — 기본값은 창구로 보내는 쪽 |
| 프린터 · 인쇄설정(컬러/겹쳐 찍기/드롭아웃) | **구현됨** |
| 초기화 시간 · 화면 배치 · 입력 장치 | **구현됨** |
| 이용통계 | **구현됨** — 개인정보 없이 집계 |
| **콘텐츠 단위 배포·갱신** | **검토 중** — 지금은 설치본 전체를 교체합니다 |
| **기관 간 개선사항 되돌려받기** | **장기 비전** — 통로가 없습니다 |

⚠️ **기관별 설정으로 뺄 수 없는 것도 있습니다.** 일반구·행정시처럼 해석이 갈리는 자리는
규칙을 정교하게 만드는 대신 **직접 적을 칸**을 두는 쪽을 택했습니다. 이 판단 기준을
앞으로도 유지합니다 — 자동 판정이 틀리면 **종이가 틀립니다.**

## 8. 서식 개정과 버전관리

법정서식은 개정됩니다. 개정되면 **좌표가 움직이고, 화면은 멀쩡한데 인쇄물만 어긋납니다.**
이것은 가정이 아니라 이 저장소에서 실제로 겪은 일입니다(`forms/naming.config.js` 머리말의
구본·신본 경고).

### 지향하는 단위 (**분리 예정**)

```
여권발급신청서 콘텐츠 v1.2
        ↓
법정서식 개정
        ↓
v1.3
```

### 개정 시 확인할 항목

| 확인할 것 | 지금 어떻게 보는가 |
|---|---|
| 서식 PDF 변경 | 사람이 원본을 대조 |
| 기재항목 추가·삭제 | 사람이 대조 |
| **좌표 변경** | `verify-print.py` 가 19쪽 픽셀로 잡습니다 — **구현됨** |
| 작성요령 변경 | 담당 부서 확인 |
| 질문 변경 필요 여부 · 분기규칙 영향 · 도움말 영향 | 사람이 판단 |
| 기존 테스트 영향 | 기준선 갱신 여부로 드러남 |
| 정상 출력 기준 변경 | `--update` 로 기준선 갱신 + 이유를 `CHANGELOG.md` 에 — **구현됨** |

> ⛔ **설명 없이 기준선을 갱신하지 않는다**는 규칙은 이미 저장소의 규칙입니다
> ([`../AGENTS.md`](../AGENTS.md) §2). 콘텐츠 단위로 쪼개더라도 이 규칙은 그대로 갑니다.

### Git 기반 이력

변경이력을 Git 으로 관리해 **언제 / 무엇이 / 왜** 바뀌었는지 확인할 수 있게 하는 방향입니다.
지금도 `CHANGELOG.md` 가 「무엇을·왜·어디를·확인」 형식으로 그 역할을 합니다 — **구현됨**.
다만 **저장소 단위**라 콘텐츠 하나만 떼어 이력을 보기는 어렵습니다(§1). 콘텐츠 단위로
끊는 것이 **분리 예정** 항목입니다.

## 9. 장기 운영모델

### 왜 「법정서식」을 단위로 삼는가

막연히 모든 행정업무를 시스템화하려는 것이 아니라, **법정 신청서라는 명확한 단위**를
기준으로 삼기 때문에 대상과 범위를 관리할 수 있습니다.

```
신청서 A · 신청서 B · 신청서 C · …
```

세는 단위가 분명하면 §4 끝의 질문들 — 무엇이 있고, 무엇이 없고, 어느 버전이고, 누가
검증했고, 어디서 쓰는가 — 에 답할 수 있습니다. **장기 유지관리와 기관 간 공유에서
이것이 가장 중요한 장점입니다.**

### 역할 분담 (**장기 비전**)

> 최초 개발자 한 사람이 모든 콘텐츠를 계속 만들고 유지하는 구조를 **목표로 하지 않습니다.**

| 주체 | 맡는 것 |
|---|---|
| **공통 플랫폼** | 공통 엔진 개발·관리 · 콘텐츠 규격 관리 · 검증체계 관리 · 배포기능 관리 |
| **업무 담당자** | 업무기준 제공 · 질문·도움말 검토 · 분기 및 예외 검토 · 변경사항 확인 · 최종 콘텐츠 검증 |
| **AI** | 분석·구조화·구현 보조 · 초안 생성 · 반복작업 감소 · 테스트 및 검증도구 제작 지원 |
| **각 기관** | 공통 콘텐츠 활용 · 기관별 운영설정 · 실제 운영 · 현장 피드백 제공 |

이 분담의 목적은 하나입니다 — **특정 개발자 한 명이 계속 직접 유지보수해야만 돌아가는
구조를 피하는 것.**

## 10. 장기 비전

> ### 플랫폼은 공통으로 제공하고, 콘텐츠는 그 업무를 가장 잘 아는 담당자가 만든다.

이 문장이 뜻하는 것과, 뜻하지 **않는** 것을 함께 적습니다.

- ⛔ **모든 공무원을 전문 개발자로 만들자는 것이 아닙니다.**
- 생성형 AI가 **구현의 진입장벽**을 낮춥니다 — 업무 판단을 대신하는 것이 아닙니다.
- 담당자가 이미 가진 **업무지식과 경험을 실제 도구로** 만들 수 있게 합니다.
- 검증된 콘텐츠를 **기관 간 공유**하고, 다른 담당자가 **개선**할 수 있게 합니다.
- 법정서식이 개정되면 **버전업**으로 따라갑니다(§8).
- 좋은 콘텐츠가 **특정 개인의 PC에서 끝나지 않고 공공의 자산으로 축적**되게 합니다.

지향하는 순환입니다.

```
현업 문제 발견
    ↓
담당자의 업무지식 구조화
    ↓
AI를 활용한 콘텐츠 제작
    ↓
현업 검증
    ↓
실제 서비스 적용
    ↓
공유
    ↓
다른 기관 활용
    ↓
현장 피드백과 개선
```

길게 보면, 공무원이 자신의 업무에서 발견한 문제를 작은 도구로 구현하고 **검증된 결과를 다른
공무원이 재사용·개선하는 공공 업무도구 생태계**로 넓어질 가능성을 열어 둡니다.

> ⚠️ **이 절은 전부 장기 비전입니다.** 지금 있는 것은 §1 이 전부이고, 이 순환을 도는
> 도구도 통로도 **아직 없습니다.**

- **콘텐츠 공유 통로가 없습니다.** §7 의 순환은 방향이지 운영 중인 체계가 아닙니다.

  참여·지원하기로 했다는 것을 **전제하지 않습니다.**
- **효과를 재지 않았습니다.** 처리시간·반려율·만족도·비용은 측정한 적이 없습니다.
  → [`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) §6

> 이 문서는 **이 프로젝트 자체의 기술·운영 방향**을 적은 것입니다.
