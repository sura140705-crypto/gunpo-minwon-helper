# 다른 서식·다른 기관으로 어떻게 넓히는가

> **제품 관점의 확장 절차**입니다. 「무엇을 정해야 하는가」와 「무엇을 검증해야 끝인가」를
> 순서대로 적었습니다.

| 이 문서 | 무엇을 정하고 무엇을 확인해야 하는가 (제품·UX 관점) |
|---|---|
| [`../engine/README.md`](../engine/README.md) | **기술 절차** — 배경 이미지·좌표맵·config·빌드 |
| [`타지자체-확산.md`](타지자체-확산.md) | **운영 절차** — 설치·환경설정·인수인계 (A/B/C 세 갈래) |
| [`UX_DECISIONS.md`](UX_DECISIONS.md) | 왜 이 구조인가 |

세 문서는 겹치지 않습니다. **이 문서는 「무엇을 정할 것인가」까지만** 말하고,
「어떻게 만들 것인가」는 위 두 문서로 넘깁니다.

---

## 0. 가장 중요한 원칙

> **새 서식을 추가할 때 화면을 새로 발명하지 않는다.
> 공통 제품 문법 안에 새로운 행정업무를 연결한다.**

새 민원이 들어올 때 우리가 만드는 것은 **화면이 아니라 질문 목록과 좌표맵**입니다.
화면은 이미 있습니다. 만약 「이 민원은 화면이 달라야 한다」는 결론이 나온다면,
그것은 새 화면이 필요한 것이 아니라 **공통 문법이 아직 그 경우를 못 담고 있다는 뜻**입니다.
그때는 서식 하나를 위해 화면을 만들지 말고 **공통 문법을 고칩니다.**

### 넓히는 방향은 둘입니다

| | 무엇 | 난이도 | 주로 보는 문서 |
|---|---|---|---|
| **A. 서식을 늘린다** | 같은 기관에서 다루는 민원을 추가 | 좌표 작업이 가장 비쌉니다 | 이 문서 §1 + `engine/README.md` |
| **B. 다른 기관이 쓴다** | 기관명·색·로고·취급 서식 교체 | **설정만으로 대부분 끝납니다** | 이 문서 §3 + `타지자체-확산.md` |

> 서식 **좌표맵은 법정 별지서식 기준이라 전국 공통**입니다. B 에서 좌표를 다시 잡을 일은
> 없습니다 — 그래서 B 는 반나절이면 끝납니다.

## 1. 새 서식을 추가하는 14단계

각 단계에 **누가 정하는가**를 함께 적었습니다. 개발자가 혼자 정할 수 없는 것이 여럿 있습니다.

### 준비 — 무엇을 만들지 정한다

**① 실제 사용할 행정서식을 확보한다** · 담당 부서
- 현재 시행 중인 **법정 별지서식 원본**(PDF·HWP)을 받습니다. 인터넷에서 주운 것을 쓰지 않습니다.
- ⚠️ 개정일자를 확인합니다. 서식이 개정되면 좌표맵을 다시 잡아야 합니다.
- `서식원본/` 에 둡니다.

**② 시민이 이해해야 할 업무 목적을 정의한다** · 담당 부서 + 설계
- 「이 민원을 하러 온 시민은 **무엇을 하려는 사람인가**」를 한 문장으로 씁니다.
- ⚠️ 목적이 **둘 이상이면 서식을 나눌지** 먼저 검토합니다. 한 서식이 두 목적을 담으면
  질문 흐름이 갈라져 복잡해집니다.

**③ citizen / formal 명칭을 분리한다** · 담당 부서 검토 필수
- **citizen** — 시민이 하려는 일. 「아이 출생 신고하기」
- **formal** — 정확한 행정서식명. 「출생신고서」
- ⚠️ **창구와 말이 통해야 하므로 둘 다 냅니다.** 시민의 말만 쓰면 창구에서 「그게 뭐죠」가 됩니다.
- ⚠️ 넓은 표현을 쓰지 않습니다. 「서류 떼기」는 주민등록 등·초본까지 포함하는 것으로 읽힙니다.

### 설계 — 무엇을 물을지 정한다

**④ 필요한 질문을 추출한다** · 담당 부서 + 설계
- 서식의 칸을 그대로 옮기지 **않습니다.** 「이 칸을 채우려면 시민에게 무엇을 물어야 하는가」로
  뒤집습니다. 한 번의 답이 **여러 칸을 채우는** 경우가 많습니다.
- 조건에 따라 **안 물어도 되는 질문**을 골라냅니다(철학 §4 One Decision at a Time).

**⑤ 행정용어를 시민 언어로 바꾼다** · 담당 부서 검토 필수
- `신청인 구분` → 「누구의 여권을 신청하시나요?」
- ⚠️ 정확한 행정용어가 꼭 필요하면 **유지하되 쉬운 설명을 먼저** 놓습니다.
- ⚠️ 문구는 확정이 아닙니다 — 카탈로그·config 한 곳에 모아 두어 갈아 끼울 수 있게 합니다.

**⑥ 질문과 실제 서식 필드를 매핑한다** · 설계 + 개발
- 답 하나가 서식의 어느 칸(들)에 들어가는지 표로 만듭니다.
- ⚠️ **인쇄 후 직접 적을 칸**(서명·날인)과 **시스템이 채우는 칸**을 여기서 가릅니다.
  둘은 종이 위에서 **다른 표시**를 씁니다(Print Marker / 값).
- 좌표를 잡는 법은 [`../engine/README.md`](../engine/README.md).

**⑦ 필요한 경우 Ready(사전 준비) 정보를 정의한다** · 담당 부서
- **경로와 무관한 공통 준비물**만 카탈로그 `ready` 에 넣습니다.
- 경로가 정해진 뒤의 준비물(성인/미성년·본인/대리)은 **그 서식 안에서** 냅니다.
- ⛔ **모든 민원에 의무적으로 두지 않습니다.** 실제 사전 확인이 필요한 경우에만 씁니다.
- ⛔ **없는 것을 지어내지 않습니다.** 비어 있으면 그 줄을 아예 내지 않습니다.

**⑧ 작성 중 계속 볼 RAIL 정보를 정의한다** · 담당 부서
- 「작성하는 **동안 내내** 참고할 가치가 있는가」가 기준입니다.
- ⛔ 「지금 해야 할 행동」을 넣지 않습니다 — 행동은 ASK 가 맡습니다.
- ⛔ 최대 2개 묶음 · 매우 짧게 · **스크롤을 요구하지 않습니다.**
- **없으면 비워 둡니다.** 억지로 채우지 않습니다. → [UX_DECISIONS ⑤](UX_DECISIONS.md)

### 구현 — 붙인다

> 손댈 때 색·조형·아이콘·RAIL·크게 보기를 **새로 정하지 마십시오** — 여권에서 이미 정했습니다.
> **상단 BAR 도 그 문서 §1-1 의 Shell 구조를 그대로 씁니다** — 업무명·직접 인쇄·초기화를
> BAR 에 두지 않고, 날짜는 최우측 고정입니다.
>
> 다음 넷은 **값이 동결돼 있습니다.** 옮길 때 그대로 가져가고, 다시 정하지 마십시오.
>
> | | 어디에 | 요점 |

**⑨ 카탈로그에 등록한다** · 개발
- `index.html` 의 `<!--FORM-CATALOG v1-->` 한 곳에만 넣습니다.
- `key`·`citizen`·`formal`·`category`·`keywords`·`aliases`·`icon`·`href` +
  ③⑦ 에서 정한 `desc`·`ready`·`scale`
- ⛔ `key` 는 환경설정(`kiosk-app/main.js` 의 `FORM_KEYS`·`admin/settings.html`)과의
  **계약**입니다. 세 곳의 이름이 같아야 합니다.
- **Main 의 CENTER 가 읽는 것**(2026.08.28 재설계) : `formal`(배지·신청서 카드) ·
  `citizen`(제목) · `desc`(준비물이 없을 때의 한 줄) · `scale`(소요) ·
  `ready[]` = `{t, s, opt, g}` — `g` 는 준비물 미니 그래픽 이름
  (`id-card`·`id-photo`·`payment`·`document`·`cert`·`passport-book`, 없으면 `document`).
  ⛔ **`ready` 를 지어내지 마십시오.** 확인된 것이 없으면 비워 둡니다 — 그러면 그 구역을
  아예 내지 않습니다(있는 것처럼 보이는 것이 없는 것보다 나쁩니다).
- 목록 아이콘은 `index.html` 의 `ICONS` 에 같은 `key` 로 넣습니다. 없으면 카탈로그의
  `icon`(이모지) → **기본 서류 아이콘** 순으로 물러납니다(빈 칸이 되지 않습니다).
- ⚠️ `preview.fields`·`preview.sample` 은 **지금 Main 이 쓰지 않습니다**(종이 미리보기
  시연 전용이었고 그 코드는 사용 중단 상태입니다). 새 서식에 넣지 않아도 됩니다.
- 미리보기 그림 : `python tools/make-form-previews.py`

**⑩ 기관 설정(SITE-CONFIG)을 적용한다** · 개발
- 기관명·대표색·로고가 새 화면에도 걸리는지 확인합니다.
- ⛔ **인쇄물에 나가는 값을 이 통로에 얹지 마십시오.** 그 순간 인쇄 회귀 안전망이 무너집니다.

### 검증 — 여기까지 해야 끝입니다

**⑪ 일반 / 크게 보기를 검증한다**
- 크게 보기에서 글자·조작 영역·간격이 함께 커지는지, 잘리는 것이 없는지.
- ⚠️ **종이가 작아지는 것은 정상입니다**(→ [UX_DECISIONS ⑧](UX_DECISIONS.md)).
  📌 다만 26/56/18 을 쓰는 화면에서는 열 폭이 고정이라 **종이가 줄지 않습니다.**
- 📌 **크게 보기의 세로 스크롤이 늘어나는 것은 허용합니다**(2026.08.28). Big 은 정보밀도보다
  **가독성이 먼저**입니다. 조건은 가로 넘침 0 · 잘림 없음 · PAPER/RAIL 침범 없음 뿐이고,
  ⛔ 스크롤을 줄이려고 글자를 다시 깎거나 컴포넌트를 압축하지 마십시오.
- **한국어 어절 중간 줄바꿈 0** 을 확인합니다 — 글자별 위치를 재면 눈으로 놓친 것도 잡힙니다.

**⑫ 인쇄 결과를 검증한다** ← **가장 중요**
```bash
python tools/verify-print.py --update     # 새 서식을 기준선에 추가 (이유를 CHANGELOG 에)
python tools/verify-print.py              # 이후로는 「전부 0px」이 기본값
python tools/verify-print.py --electron   # 실제 인쇄 경로 + 용지(A4)
```
- 새 서식은 **작성예시 2벌**을 만들어 기준선에 넣습니다.
- ⚠️ 작성예시는 **전부 가상 인물**이어야 합니다.

**⑬ 개인정보 Clear 를 검증한다**
- 무동작 3분 → 30초 경고 → 첫 화면 이동, 값 소멸
- 인쇄 후 즉시 덮기 → 5초 뒤 첫 화면
- 새 서식이 값을 어딘가에 남기지 않는지 (저장소를 쓰지 않아야 합니다)

**⑭ 완료 후 Main 복귀를 검증한다**
- 인쇄·초기화 뒤 `index.html` 로 돌아오고, **3분 뒤 시연(선택 자동 순회)이 다시 도는지.**
  새 서식도 그 순회에 **끼어 있는지**(끈 서식은 빠집니다 — `formOn`).
- 돌아온 화면에 **앞사람 흔적이 없는지.**
- 서식이 많아졌다면 **크게 보기에서 목록이 구를 때 [직원에게 여쭤볼게요] 단추가
  기둥 바닥에 남아 있는지.** 그 단추가 화면 밖으로 밀리면 시민이 갇힙니다.

### 그 밖에 반드시 돌리는 것

```bash
bash tools/sync-kiosk.sh          # 루트 → kiosk-app/app 동기화
bash tools/sync-kiosk.sh --check  # 드리프트 확인
python tools/check-site-block.py     # 기관 설정 블록이 모든 화면에서 같은지
python tools/check-design-tokens.py  # 디자인 토큰이 모든 화면에서 같은지
python tools/verify-site-config.py   # 설정이 화면에 실제로 걸리는지
```

> ⚠️ 서식이 하나 늘면 위 검사들이 보는 **화면 수가 9 → 10** 이 됩니다. 도구가 세는 숫자도
> 함께 확인하십시오.

## 2. 새 서식을 추가할 때 흔히 하는 실패

| 실패 | 왜 생기나 | 어떻게 막나 |
|---|---|---|
| **서식의 칸을 그대로 질문으로 옮긴다** | 서식 순서 = 질문 순서라고 생각하기 쉽습니다 | ④ 로 뒤집습니다. 답 하나가 여러 칸을 채웁니다 |
| **행정용어를 그대로 쓴다** | 담당자에게는 익숙한 말입니다 | ⑤ 를 **담당 부서가 아닌 사람**에게 읽혀 봅니다 |
| **RAIL 을 억지로 채운다** | 비어 보이는 것이 불안합니다 | ⑧ — 비우는 것도 결정입니다 |
| **준비물을 지어낸다** | 다른 서식에 있으니 이것도 있어야 할 것 같습니다 | ⑦ — 없으면 그 줄을 내지 않습니다 |
| **인쇄 검증을 마지막에 한 번만** | 좌표가 다 끝나야 볼 수 있다고 생각합니다 | ⑫ 를 **작업 중에 계속** 돌립니다 |
| **`key` 를 나중에 바꾼다** | 이름이 마음에 안 듭니다 | ⑨ — 세 곳의 계약입니다. 처음에 정합니다 |
| **화면을 새로 만든다** | 이 민원은 특별해 보입니다 | §0 — 공통 문법을 고칠 일인지 먼저 봅니다 |

## 3. 다른 기관이 가져다 쓸 때

**절차는 [`타지자체-확산.md`](타지자체-확산.md) 에 있습니다.** 여기서는 **제품 관점에서
반드시 정해야 하는 것**만 적습니다.

| 정할 것 | 왜 중요한가 |
|---|---|
| **취급하는 서식** | 취급하지 않는 민원을 켜 두면, 시민이 **다 작성한 뒤 창구에서 되돌아갑니다.** 여권처럼 시·군·구청만 취급하는 것에 주의 |
| **대표색** | 화면 색 전체가 여기서 계산됩니다. 하나만 고르면 됩니다 |
| **기관명·부서·연락처·로고** | 화면에만 나옵니다. **인쇄물에는 나오지 않습니다** |
| **업무 기준**(여권 접수 등) | 기관마다 다릅니다. **확실하지 않으면 기본값**(창구로 보내는 안전한 쪽)을 두십시오 |

## 4. 확장해도 바뀌지 않는 것

새 서식이 들어와도, 다른 기관이 가져가도 **이것만은 같습니다.** 시민이 사용법을 다시
배우지 않아도 되는 이유입니다.

```
서식 선택 → (필요하면) 준비 확인 → 쉬운 질문 → 실제 Paper 반영 → 검토 → 인쇄 → Clear → Main
```

- 세 영역의 **역할** (ASK / PAPER / RAIL)
- **시민의 말로 묻고** 시스템이 행정서식으로 번역한다
- 내가 적은 것이 **종이 어디에 들어가는지** 보인다
- 틀리고 나서 알려주기보다 **틀리지 않게** 한다
- 막히면 **직원에게 가는 길**이 있다
- 끝나면 **개인정보가 사라지고 첫 화면으로** 돌아온다
