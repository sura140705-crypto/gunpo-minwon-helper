## 1. 지시서 총평

**방향은 옳다.** 특히 세 가지는 이 프로젝트가 원래 가려던 곳보다 한 발 더 나아간 판단이다.

- **창구 전환을 「실패」가 아니라 정상 완료 유형으로 설계한 것.** 지금은 특수 사례를 끝까지
  끌고 가다 창구에서 되돌려보내는데, 그게 시민에게도 직원에게도 가장 나쁘다.
- **빈칸을 6가지 상태로 나눈 것.** 현재는 「값이 없다」 하나뿐이라, 일부러 비운 칸과 빠뜨린 칸을
  구별하지 못한다. 이건 실제로 있는 문제다.
- **주민등록번호를 키오스크에 안 넣을 선택권.** 공용 화면에 주민번호를 치기 싫은 시민이 있다.

아래는 **착수 전에 정리하지 않으면 실제로 사고가 나거나 되돌아가야 하는 것들**이다.
문제를 심각도 순으로 적는다.

## 2. 🔴 P0 — 착수 전 반드시 결정해야 하는 것

### P0-1. 겹쳐 찍기 모드와 2쪽 출력이 정면으로 충돌한다

**이것이 가장 큰 위험이다.**

현재 키오스크는 여권을 **겹쳐 찍기(오버레이) 모드**로 인쇄한다. 기본값이 그렇다
(`kiosk-app/print-options.js` : `DEFAULT_OVERLAY_FORMS = ['passport']`).

겹쳐 찍기란 **미리 인쇄된 여권 서식 용지를 트레이에 넣어 두고, 배경을 숨긴 채 값만 찍는** 방식이다.
여권 서식이 적색 드롭아웃 용지라 흑백 프린터로는 판독이 안 되기 때문에 도입한 임시 방편이다.

그런데 이 모드는 **한 인쇄 작업의 모든 쪽에 적용된다.** 트레이에는 한 종류의 용지만 들어간다.
그래서 이런 일이 벌어진다.

| 인쇄물 | 트레이의 용지 | 결과 |
|---|---|---|
| 신청서 1쪽 | 미리 인쇄된 여권 서식 | ✅ 의도대로 |
| **법정대리인 동의서(2쪽)** | 미리 인쇄된 여권 서식 | ❌ **여권 신청서 용지 위에 동의서 글자가 찍힌다** |
| **창구 안내표(§18)** | 미리 인쇄된 여권 서식 | ❌ **여권 신청서 용지 위에 안내표가 찍힌다** |

이 위험은 이미 코드에 경고로 적혀 있다(`print-options.js` 27~29행: "2쪽짜리 서식에 이 모드를
켜기 전에 용지 운영을 먼저 정해야 한다").

**지시서는 이 문제를 두 배로 키운다.** 경로 B(미성년 자녀)를 **주경로 둘 중 하나**로 올렸고,
창구 안내표라는 **세 번째 인쇄물**을 새로 만든다.

**결정이 필요하다 — 셋 중 하나.**

1. **컬러 프린터를 도입**해 겹쳐 찍기를 끈다. 근본 해결이지만 예산·일정이 걸린다.
2. **적색 드롭아웃 흉내내기 모드로 전환**한다(이미 구현돼 있다). 미리 인쇄된 용지가 필요 없어
   2쪽·안내표 문제가 사라진다. 다만 **접수처 스캔 판독을 실물로 확인**해야 한다.
3. **용지 운영으로 푼다** — 동의서·안내표가 나올 때는 백지 트레이로 바꾸는 식. 현실성이 낮다.

> **이 결정 전에는 경로 B와 창구 안내표를 완성해도 현장에 못 올린다.** 개편의 다른 부분과
> 병행할 수는 있지만, 담당자에게 지금 물어야 한다.

### P0-2. 터치 전용인데 글자를 칠 방법이 없다

지시서 §6은 「터치 우선」, §25는 화면 키보드를 **7단계(마지막)** 로 미뤘다. 그런데
성명·주소·로마자·긴급연락처는 **결국 글자를 쳐야 한다.**

- 현재 키오스크(Electron)에는 **화면 키보드가 없다.** 물리 키보드에 의존한다.
- 윈도우 기본 터치 키보드를 쓰면 **키오스크 전체화면을 덮고**, 그 위에서 시민이 다른 조작을 할
  여지가 생긴다(현재 보안 설계는 창 이탈을 감지해 첫 화면으로 되돌린다 — 충돌 가능).
- 직접 만들면 **한글 조합(두벌식)** 을 구현해야 한다. 적은 일이 아니다.

**이건 마지막에 붙일 장식이 아니라 화면 설계를 좌우하는 선행 조건이다.** 입력 방식이 정해져야
「한 화면 = 한 가지 판단」의 화면 수와 배치가 정해진다.

**물어야 할 것**: 터치 모니터를 넣어도 **물리 키보드를 함께 둘 것인가?** 둔다면 이 문제는
대부분 사라지고(§24의 관리자 단축키 노출 문제만 남는다), 안 둔다면 화면 키보드가 **1순위**다.

### P0-3. 주민번호를 안 받으면 나이를 알 수 없다

지시서 §7의 「인쇄 후 직접 작성」은 좋은 아이디어지만, 주민등록번호는 이 앱에서
**나이를 아는 유일한 근거**다(`deriveState()`). 안 받으면 아래가 전부 무너진다.

| 주민번호에 의존하는 것 | 없으면 |
|---|---|
| 미성년 판정 → 법정대리인 동의서 출력 여부 | **동의서가 안 붙는다** |
| 유효기간 10년/5년 자동 규칙 | 미성년에게 10년이 선택 가능해진다 |
| 만 8세 미만 수수료 구분 | 예상 수수료가 틀린다 |
| 동의서의 「신청인 주민등록번호」 칸 | 빈칸 |

**다행히 새 구조가 이 문제를 상당 부분 푼다** — 경로 A/B를 시민이 **먼저** 고르므로 미성년
여부는 주민번호 없이도 안다. 그래서 동의서 출력 여부는 안전하다.

**남는 것은 나이다.** 두 가지 중 하나로 정해야 한다.

- **(권장) 경로 B는 유효기간을 5년으로 고정**한다. 미성년은 어차피 5년이므로 나이가 필요 없다.
  만 8세 미만 수수료 구분만 포기하고 「수수료는 창구 안내」로 표시한다.
- 또는 주민번호를 안 받을 때 **생년월일만 따로 묻는다**. 개인정보 부담이 훨씬 적고 나이는
  정확해진다. 다만 화면이 하나 늘고, 신청서에는 인쇄되지 않는 질문이 된다.

## 3. 🟡 P1 — 담당자 확인이 필요한 것 (개발자가 정할 일이 아니다)

### P1-1. 로마자 성명을 빈칸으로 인쇄해도 접수가 되는가 (§9)

지시서는 기존 여권이 있고 같은 이름을 쓰면 **로마자 칸을 비워서** 출력하라고 한다
(「기존자료 활용」). 그런데 로마자 성명은 여권발급신청서의 **필수 기재란**이다.

- 접수 창구가 실제로 빈칸을 받아 주는가?
- 아니면 직원이 기존 여권을 보고 대신 적어 주는가?
- 판독기가 그 칸이 빈 신청서를 어떻게 처리하는가?

**받아 주지 않는다면 이 설계는 오히려 반려를 늘린다.** 담당자 확인 없이 구현하면 안 된다.

### P1-2. 미성년 신청서의 연락처 칸에 법정대리인 번호를 넣는 게 맞는가 (§12)

지시서 §12는 자녀 번호 대신 법정대리인 번호를 쓰라고 한다. 화면 문구만의 문제가 아니라
**법정 서식 칸의 의미**를 정하는 일이다. 그 칸이 「신청인 본인의 연락처」인지 「연락 가능한
전화번호」인지에 따라 답이 갈린다.

구현 자체는 쉽다(`phone` 필드에 무엇을 넣느냐일 뿐). **행정적으로 맞는지만 확인하면 된다.**

### P1-3. 대리 신청을 전부 창구로 보내면 얼마나 잘려 나가는가 (§4)

지시서는 성인 대리 신청을 **전면 창구 전환**으로 돌린다. 이미 만들어 둔 위임장 기능을
버리는 결정이기도 하다.

- 실제 창구에서 **대리 신청이 차지하는 비중**은 얼마인가?
- 자녀가 부모 여권을 대신 신청하는 경우가 흔하지 않은가?

비중이 크면 키오스크 효용이 크게 깎인다. **숫자를 듣고 정해야 한다.**
(위임장 인쇄 로직 자체는 지우지 말고 남겨 두기를 권한다 — 정상 경로에서 호출만 안 하면
되고, 나중에 되살릴 때 비용이 0이다. 지시서 §15도 그것을 허용하고 있다.)

### P1-4. 긴급연락처를 막으면 못 넘어가는 시민이 생긴다 (§14)

지시서는 「긴급연락처 = 신청자 연락처」를 **오류로 차단**하라고 한다(§26에도 "중복 허용" 금지).
방향은 맞다 — 지금은 경고만 뜨고 그냥 넘어간다.

그런데 **다른 번호를 댈 수 없는 시민이 실재한다**(1인 가구, 고령자, 가족과 연락이 닿지 않는 경우).
완전히 막으면 그 사람은 키오스크에서 갇힌다.

**권장**: 차단하되 **「그래도 진행」 대신 「창구 확인(P-99)」 탈출구**를 둔다. 개인정보를 더
받지 않고 창구로 넘기면 지시서 §16의 철학과도 맞는다.

### P1-5. 경로 선택과 주민번호가 충돌하면 (지시서에 없음)

시민이 **「제 여권」(경로 A)** 을 골랐는데 주민번호가 **미성년**으로 나오면? 반대로
**「미성년 자녀」(경로 B)** 를 골랐는데 자녀 주민번호가 **성인**이면?

지시서에 정의가 없다. 반드시 정해야 한다. **권장 — 조용히 고치지 말고 알려서 고치게 한다.**
2020.10 주민번호 체크섬 폐지로 오탈자를 잡을 수단이 없어졌는데, **앞단의 경로 선택이 그
역할을 대신할 수 있다.** 조용히 보정하면 그 신호를 버리는 셈이다.

> 예) "앞에서 「제 여권」을 선택하셨는데, 입력하신 주민등록번호는 만 18세 미만입니다.
> 주민등록번호를 다시 확인해 주시거나, 미성년 자녀 신청으로 바꿔 주세요."

### P1-6. 최종 확인 화면에서 연락처를 가리면 오타를 못 잡는다 (§22)

§22 예시가 `연락처 010-XXXX-XXXX` 로 마스킹돼 있다. 최종 확인 화면의 **존재 이유가 오타
확인**인데 가려 놓으면 확인할 수가 없다. 인쇄물에는 어차피 전체가 찍힌다.

**권장**: 최종 확인 화면에서는 **전체를 보여준다.** 가려야 할 것은 창구 안내표(§19)이고,
그건 지시서가 이미 올바르게 규정하고 있다.

## 4. 🟢 P2 — 분리하기를 권하는 것

### P2-1. 폰트 변경(§21)은 별도 작업으로 떼라

「1이 7처럼 보인다」는 판독성 문제로 다뤄야 한다는 지적에 동의한다. 다만 이건 **개편과 성격이
전혀 다른 작업**이다.

- **인쇄물이 실제로 바뀐다.** 이 개편의 나머지 부분은 "화면만 바꾸고 인쇄물은 그대로"가
  목표라 `verify-print.py` **19쪽 0px** 이 안전망으로 계속 작동한다. 폰트를 건드리면
  **그 기준선이 통째로 깨진다.** 두 변경이 한 커밋에 섞이면 어느 쪽이 인쇄물을 바꿨는지
  구별할 수 없다.
- **격자칸 글자 크기는 칸 폭에서 계산**된다(`Math.min(cellW,h)*0.62`). 글꼴이 바뀌면 같은
  크기라도 **글자 폭이 달라져 칸을 넘칠 수 있다.** 주민번호 13칸·로마자 16칸이 특히 위험하다.
- 공용 CSS를 건드리면 **8종 전부**에 영향이 간다.

**권장 순서**: 개편을 먼저 끝내 19쪽 0px 을 확인한 뒤, 폰트만 단독으로 바꾸고
실물 인쇄 → 접수처 판독 확인 → `--update` 로 기준선 갱신 → 사유를 `CHANGELOG.md` 에 기록.

### P2-2. 여권만 바뀌면 8종의 조작법이 갈린다

여권이 아이콘·터치 방식이 되고 나머지 7종이 지금 그대로면, 같은 키오스크 안에서 **화면마다
쓰는 법이 다르다.** 창구 직원이 안내하기 어려워지고 매뉴얼도 두 벌이 된다.

여권을 기준 모델로 먼저 만드는 것에는 동의한다(지시서도 그렇게 말한다). 다만
**나머지 7종을 언제 맞출지**를 지금 계획에 넣어야 한다. 특히 허브 첫 화면(`index.html`)은
8종 공통이라 여권만 바꿀 수 없다.

## 5. §28 요구 분석 — 10항목

### ① `state.data` 전체 필드와 새 시나리오에서의 쓰임

전체 28개. **하나도 삭제하지 않아도 된다.**

| 필드 | 새 시나리오 | 비고 |
|---|---|---|
| `kind` `pages` `period` `travelType` | 사용 | 특수여권은 P-04 로 전환 |
| `nameKor` `jumin` `phone` | 사용 | 경로 B 에서 `phone` = 법정대리인 번호(P1-2) |
| `emgName` `emgRel` `emgPhone` | 사용 | |
| `hasPassport` | 사용 | 「모름」 → P-05 전환 |
| `romanSur` `romanGiven` | 사용 | 기존 여권 + 같은 이름이면 **빈칸 유지**(P1-1) |
| `regBase` `spouseRoman` `braille` | 사용(선택) | 「필요한 추가 선택사항」 |
| `mailService` `mailAddr` | 사용 | |
| `applyBy` | **사용 — 매우 중요** | 아래 ⑥ 참조 |
| `agentName` | 사용 | 경로 B 에서 **법정대리인 성명** |
| `guardianRel` `guardianJumin` `applicantAddr` `guardianAddr` `guardianName` | 사용 | 동의서용 |
| `agentBirth` `agentAddr` `agentPhone` | **미사용** | 위임장 전용. 빈 문자열로 두면 됨 |

**UI 상태는 `state.data` 밖에 둔다.** 지시서 §2.1 예시대로 `state.ui = { path, fieldStatus,
counterReason … }` 를 새로 만들고, **인쇄층은 절대 그것을 읽지 않게** 한다. 이 분리를 지키면
`verify-print.py` 19쪽 0px 이 개편 내내 안전망으로 살아 있다.

### ② 위임장 전용 필드와 로직

- **전용 필드**: `agentBirth` · `agentAddr` · `agentPhone` (3개)
- **공용 필드**: `agentName` · `guardianRel` (동의서와 함께 씀 — 지우면 안 된다)
- **로직**: `needsProxy(d)` = `applyBy==="대리인" && !needsConsent(d)` →
  `renderProxy()` → `body.needs-proxy` → CSS `.proxy-page{display:block}` + `page-break-before`
- **9단계 `condInputs`** 중 5개가 위임장용

**중요**: 새 흐름에서 「성인 + 대리인」 조합이 발생하지 않으므로 `needsProxy` 는 **항상 false**가
되고 위임장은 **저절로 호출되지 않는다.** 코드를 지울 필요가 없다.

⚠️ 단, `fillSample("minor")` 가 `applyBy:"대리인"` 을 넣는다. 테스트 데이터를 새 구조에 맞춰
손봐야 한다.

### ③ 법정대리인 동의서의 필드와 출력 연결

- **판정**: `needsConsent(d)` = `deriveState(d).ageKnown && isMinor` — **주민번호로만** 판정한다
- **출력**: `renderConsent()` → `body.needs-consent` → `.consent-page{display:block}` +
  `page-break-before:always`
- **쓰는 값**: `nameKor` · `jumin` · `applicantAddr` · `guardianJumin` · `guardianRel` ·
  `guardianAddr`(없으면 `applicantAddr`) · **법정대리인 성명 = `applyBy==="대리인" ? agentName : guardianName`**
- **빈칸으로 두는 것**: 법정대리인 2(공동친권자) 전부, 서명란

> ⚠️ **새 구조에서 판정 근거를 바꿔야 한다.** 지금은 주민번호가 유일한 근거인데, 경로 B 에서
> 주민번호를 「직접 작성」으로 비우면 **동의서가 안 붙는다.** `needsConsent` 를
> **경로 선택(`state.ui.path === 'minor'`)** 기준으로 바꾸되, 주민번호가 있으면 교차 검증하는
> 형태가 맞다. — 이것이 인쇄층에 손을 대야 하는 **거의 유일한 지점**이다.

### ④ 로마자 입력·추천 로직

- `buildRomanSuggestion()` — 한글 성명에서 로마자 후보를 만들어 **[이 예시 적용]** 버튼 제공.
  **자동 확정하지 않는다**(참고용임을 명시).
- `hasPassport` 값에 따라 문구가 갈린다: 「있음」이면 기존 여권과 똑같이 쓰라는 강한 경고,
  「모름」이면 확인 안내.
- 입력칸은 `upper:true` 로 자동 대문자.

새 시나리오의 §9 분기(없음→입력 / 있음+같은이름→생략 / 있음+다른이름→P-03 / 모름→P-05)와
**충돌하지 않는다.** 추천 기능은 「기존 여권 없음」 경로에서만 보여주면 된다.

### ⑤ 미성년 판정 로직

`deriveState(d)` — 순수 함수, 저장 없음.

- 주민번호 앞 7자리로 생년월일 + 세기/성별 코드 판독 (1·2·5·6→1900, 3·4·7·8→2000, 9·0→1800)
- **체크섬은 쓰지 않는다** — 2020.10 이후 발급분에서 폐지되어, 검증에 쓰면 정상 번호를 오탈락시킨다
- `age < 18` → `isMinor`
- `applyAgeRules()` 가 미성년이면 `period` 를 **10년 → 5년으로 덮어쓴다** ← 지시서가 없애려는
  「고른 값이 뒤에서 바뀌는」 동작이 바로 이것이다. 경로 B 에서 5년만 보여주면 이 함수는 필요 없어진다.

### ⑥ 신청자·서명란 결정 로직

`renderForm()` 안 한 줄이다.

```js
const signer = (d.applyBy==="대리인" && d.agentName) ? d.agentName : d.nameKor;
```

**이 한 줄이 새 시나리오를 그대로 만족시킨다.**

| 경로 | `applyBy` | `agentName` | 서명란 | 동의서 | 위임장 |
|---|---|---|---|---|---|
| A 성인 본인 | `"본인"` | `""` | 신청인 본인 | ✗ | ✗ |
| B 미성년 자녀 | `"대리인"` | 법정대리인 성명 | **법정대리인** ✅ | **✅** | ✗(needsConsent 우선) |

즉 **경로 B는 `applyBy="대리인"` + `agentName=법정대리인 성명` 으로 채우기만 하면 서명란·동의서·
위임장이 전부 의도대로 나온다.** 인쇄층을 고칠 필요가 없다. (지시서 §13의 "같은 이름을 다시
입력시키지 않는다"도 이 구조로 자연히 충족된다.)

### ⑦ 연락처·긴급연락처 검증

- **2단계 `validate`** — 주민번호 13자리 미만/형식 오류, 연락처 10자리 미만을 **경고 문구**로 표시
- **6단계 `warn`** — 긴급연락처 == 본인 연락처면 경고. **숫자만 뽑아 비교**(`replace(/\D/g,"")`)
  하므로 지시서 §14의 "하이픈 제거 후 비교" 요구는 **이미 충족**돼 있다
- ⚠️ **둘 다 막지 않는다.** 경고만 뜨고 [다음]으로 넘어간다. 지시서대로 차단하려면 `tryAdvance()`
  단계에서 막아야 한다 → **P1-4의 탈출구를 반드시 함께 설계할 것**

### ⑧ 개인정보 초기화가 실행되는 모든 지점

현재 5곳이다.

| # | 계기 | 동작 |
|---|---|---|
| 1 | [초기화] 버튼 | 확인창 → `state = createEmptyState()` (**페이지 이동 없음**) |
| 2 | 3분 무동작 | 30초 카운트다운 경고 → `location.href="index.html"` |
| 3 | 인쇄 직후(`afterprint`) | 전체화면 가림막 → 5초 뒤 허브로 이동 |
| 4 | 키오스크 창 이탈 | `kiosk-app/main.js` 가 첫 화면으로 되돌림 |
| 5 | 페이지 이동 자체 | 값이 메모리에만 있으므로 이동하면 소멸 |

⚠️ **2·3·4는 「허브로 이동」이고 1만 「같은 페이지에서 상태 초기화」다.** 새 UI가 화면 전환을
자체 라우팅으로 하더라도 이 메커니즘을 유지해야 한다.

**새로 필요한 것** — 지시서 §20의 **창구 전환 후 초기화**. 안내표 인쇄 또는 [처음으로] 이후에
`state` 를 비워야 하고, **창구 코드만으로 개인정보를 복원할 수 없어야 한다**(§20). 지금 구조는
값이 메모리에만 있어 이 요구를 자연히 만족한다 — **안내표에 개인정보를 넣지 않기만 하면 된다.**

⚠️ `afterprint` 는 **인쇄와 취소를 구분하지 못한다**(브라우저 공통). 취소해도 초기화된다.
창구 안내표 인쇄에도 같은 제약이 걸리므로, 안내표를 인쇄하면 그 뒤 화면이 사라진다는 점을
설계에 반영해야 한다(시민이 사진을 찍기 전에 화면이 없어지면 안 된다).

### ⑨ 기존 인쇄 로직과 충돌할 가능성이 있는 부분

1. **겹쳐 찍기 × 2쪽·안내표** — P0-1. 가장 크다.
2. **`needsConsent` 가 주민번호에만 의존** — ③ 참조. 판정 근거 변경 필요.
3. **`applyAgeRules()` 의 값 덮어쓰기** — 경로 B에서 5년 고정하면 불필요해진다.
4. **`fillSample()` 의 테스트 데이터** — `applyBy:"대리인"` 등 새 구조와 어긋난다.
5. **창구 안내표의 인쇄 경로** — 신청서와 다른 문서다. 현재 인쇄 CSS는 `.stage`(A4 서식) 기준으로
   짜여 있어, 안내표는 **별도 페이지 규칙**이 필요하다. `@page{size:A4;margin:0}` 을 공유하므로
   여백 0에서 큰 글씨를 어떻게 배치할지 정해야 한다.
6. **`window.__printNotice` 모달** — 인쇄 직전 안내창이 공용 스니펫이다. 안내표 인쇄에도 같은
   모달("여백 없음·배율 100%")이 뜨면 어색하다. 분기 필요.

### ⑩ 최소 변경으로 되는 것 / 리팩터링이 필요한 것

| 영역 | 판단 | 이유 |
|---|---|---|
| **좌표맵 `CO`** | 🟢 **손대지 않음** | 법정 서식. 지시서 §2.2 |
| **`renderForm()`** | 🟢 손대지 않음 | `state.data` 만 읽는다 |
| **`renderProxy()`** | 🟢 그대로 두고 호출 안 됨 | `needsProxy` 가 항상 false |
| **`renderConsent()`** | 🟡 **판정 근거 한 줄만** | `needsConsent` 를 경로 기준으로 |
| **`deriveState()` / `formatJumin` 등** | 🟢 그대로 재사용 | 순수 함수 |
| **`STEP_DEFS` 10단계 배열** | 🔴 **교체** | 고정 배열 → 조건부 라우팅 |
| **`renderStep()` / `tryAdvance()` / 스텝퍼** | 🔴 교체 | 새 화면 모델 |
| **화면 CSS(코치 패널)** | 🔴 교체 | 터치 기준 재설계 |
| **인쇄 CSS(`@media print`)** | 🟡 **거의 손대지 않음** | 안내표 페이지 규칙만 추가 |
| **유휴·인쇄 후 초기화 스니펫** | 🟢 유지 | 8종 공용. 건드리면 나머지 7종과 갈라진다 |

**요약하자면 — 인쇄층은 거의 그대로 두고, 질문 흐름 층만 갈아 끼우면 된다.** 이 프로젝트가
원래 그렇게 분리돼 있어서 가능한 일이다. 지시서 §2.1의 판단이 정확했다.

## 7. 제안하는 착수 순서

지시서 §25의 순서에 대체로 동의한다. 다만 **P0 결정을 앞으로 당기고**, 검증 지점을 끼워 넣었다.

```
0. 담당자 확인 — 위 질문 1·2·3 (나머지는 병행 가능)
1. state.ui 상태 모델 + 라우터 골격      ← 인쇄층은 건드리지 않음
2. 경로 A(성인 본인) 끝까지 완성          ← 여기서 verify-print 19쪽 0px 확인
3. 경로 B(미성년) + 동의서 판정 근거 변경  ← 인쇄층에 손대는 유일한 지점, 재확인
4. 창구 전환 + 사유 코드                  ← 안내표 인쇄는 P0-1 결정 후
5. 터치 UI 정리 (키보드 결정에 따라)
6. 최종 인쇄 회귀 + 실물 인쇄 검수
```

**2번과 3번 사이에서 반드시 `python tools/verify-print.py` 로 19쪽 0px 을 확인한다.**
경로 A만 끝난 시점에 인쇄물이 그대로면, 그 뒤 무엇이 인쇄물을 바꿨는지 정확히 짚을 수 있다.
